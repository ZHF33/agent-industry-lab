# Day 027 异常与错误阅读

## 单据读不出来时，应该记录什么

调度员收到一张破损的预约单，编号和时间无法辨认。可以退回补单并继续处理另一张。若调度软件本身打不开，不能替它填一张空白并记作成功。类比区分坏资料和处理故障，真实程序要靠错误类型和发生位置判断，单靠报错口气不能确认原因。

本课用 JSON 演示。它是一种有规则的文本形式，可以用成对的花括号和有名字的字段写一条预约，例如 {"id":"A"}。读入的动作叫解析，也就是把文本转成 Python 能读写的对象。Python 遇到无法继续的情况会产生异常，一个带类型、说明及调用位置的错误信号。

## 代码怎样处理错误

脚本第一层 decode_booking 调用 JSON 解析器。第二层 review_line 用 try 标出尝试执行的语句。如果解析成功，跳过 except，读出编号。如果解析器产生 JSONDecodeError，程序转到对应 except，提取原文本的行列位置。其他异常继续向外传递，能让调用者发现不同故障。以下是讲解片段，完整定义和导入见脚本。

```python
try:
    booking = decode_booking(raw)
except json.JSONDecodeError as error:
    return f"invalid_json line={error.lineno} column={error.colno}"
return f"decoded {booking['id']}"
```

手推：输入 {"id":"A"}，解析成功，进入最后一行。只把输入改成单独的左花括号，解析器读到文末，期待字段或闭合符，抛出异常。外层捕获它，给出第 1 行、第 2 列。这个位置指原始资料，和下面 traceback 中的 Python 源代码行号用途不同。

**小问题**　输入 {} 会发生什么？

**解释**　花括号成对，所以 JSON 解析成功。读编号时会产生 KeyError，表示键不存在。这属于字段契约问题，当前程序会让它冒泡。工程上应另做字段校验，给调用者可用的退回原因。

## 从错误类型定位到调用点

Traceback 是异常向外传播时留下的调用记录。先读最末行的错误类型和消息，知道失败类别；再从调用记录靠后的部分向前找自己文件中的调用位置；最后检查当时传入的原始文本。如果错误类型为 JSONDecodeError，消息中的行列号用于原文本。如果类型是 KeyError，应先查字段来源和读取位置。

**小问题**　把整个程序用通用 except 包住，出错直接返回“处理成功”，哪里会出问题？

**解释**　业务方会把失败当作成功，并失去具体位置。经常可预期的资料错误适合明确捕获并打上失败状态。遇到其他异常时，程序或调用方应保留失败信号，日志如果要面向外部，还需先处理敏感输入。

## 给 Agent 留一条可复核的失败路径

在装卸月台 Agent 中，工具参数错误会成为可审计的工具结果，提示模型纠正。模型协议结构不合法或耗尽轮次时，任务以失败响应结束，人审不会拿到被伪装成成功的报告。实作验收时画出“资料来源 → 解码 → 字段检查 → 容量计算 → 调度员复核”，并标出每一处的失败去向。对照答案是格式坏退回来源，字段缺失交业务核对，计算成功且证据可用才交人审。
