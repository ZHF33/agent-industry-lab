# 第十三期｜回答是合法JSON，为什么仍然不能验收？

前置[第11期任务卡](day-011.md)、[第12期资料与指令](day-012.md)。本期目标：分清能解析、契约符合、内部一致、证据支持与业务许可五个层次，不把一个格式检查当全部正确。

## 1. 一张填得整齐的表，也可能填错

制造人员要调查原料A下游，模型返回一张整齐表格：“候选3批次，已经全部召回”。格式好读，却至少有两个问题：三批次是否有证据，以及程序是否真的有召回权限并执行成功。

类比报销单：金额栏填的是数字，表格签名齐全，不自动证明发票真实或款项已支付。类比边界：本课处理程序字段与模型结果，不讨论任何具体财务政策；实际权限由业务系统决定。

输出格式解决“怎样读”，验收解决“按什么证据接受到哪一步”。把这两件事分开，才能知道失败应回到模型、校验器、资料还是执行流程。

## 2. JSON究竟保证什么？

JSON用花括号表示对象、键值表达字段、方括号表示列表。例如candidate_count是数量字段，candidate_lots是批次列表，actions_executed是是否执行的布尔标记。

**解析**是把JSON文本读成程序对象。少了右括号可能解析失败；字段值是数字3或字符串"3"都可以是合法JSON，但业务契约可能只接受数字。JSON语法本身不知道“候选批次数”应该是多少，更不知道真实生产记录。

模型可以被提示输出JSON，也可以在支持的接口里使用结构化输出机制；无论哪种，格式限制不能补出资料缺失、授权或真实执行证据。前几期的生成原理仍成立：输出来自条件生成，不能因为文本可解析就变成独立事实。

小问题：`{"count":"三个"}`是合法的吗？在JSON语法上合法；若契约要求整数，则契约失败。先说清检查层次，别只说“JSON错了”。

## 3. 五层验收门

| 层次 | 本期问题 | 错误例子 |
| --- | --- | --- |
| 语法 | 能解析成对象吗 | 只有左括号 |
| 契约 | 字段、类型、必填符合吗 | 数量写成字符串 |
| 内部一致 | 字段之间自洽吗 | count=2却列3个批次 |
| 证据支持 | 对应当前证据吗 | 列一个来源没有的批次 |
| 动作与许可 | 是否有真实动作和权限依据 | 无执行器却声称已召回 |

本期接受到“可交人工审查”，不是“可以执行”。人工仍要核来源完整性、业务规则和建议合理性。现有Agent人审只接受报告，不执行召回。

**契约**是双方约定的结构和含义；**不变量**是在一个结果中必须同时成立的关系，例如count等于列表长度。写这些关系，能让验收摆脱“看起来不错”。

## 4. 用小数字推导内部一致

设L为候选列表，n为candidate_count。要求n为非负整数，n=len(L)，并且L无重复。len表示元素个数；若L=[B,C,D]，len(L)=3，所以n=2应拒绝。

去重后的集合大小也要等于列表长度。L=[B,B,C]长度3，但不同批次只有2个，不能把重复条目当3个批次。如果业务允许同一批次按不同关系重复，那应换成另一份明确契约；不能在同一报表里混口径。

Python里True可在某些场景像整数1工作，本例用`type(value) is int`，避免布尔值被当数量。此处不是所有代码都必须这样写，而是本课堂采用严格类型口径。

## 5. 自洽为什么仍可能错误？

真实的合成证据期望B、C、D，模型写OTHER、C、D，数量3且无重复，但证据不支持。我们将列表转为集合，与本次固定期望集合比较，结果不等就拒绝。

这只适合本课的小型、确定合成结果；真实开放任务未必有唯一标准答案。更复杂验收可能要核每条来源、条件、时效、范围及无答案情况，而不能只和一段参考文字逐字相等。

另外，三跳搜索本身被截断。即使模型完整复述三批次，也不能说“全部受影响批次就是三个”。正确输出需保留范围限定；今天[批次影响Agent](../../examples/lot-impact-review/README.md)另外输出frontier_edges与limitations。本课堂校验器为了讲清层次，只核三个字段，不覆盖Agent完整报告。

小问题：校验器用的期望集合本身错了会怎样？它会把错误标准执行得很稳定。所以验收标准也要有来源和复核，不能因为是程序算的就不审查。

## 6. 动作声明也需要证据

actions_executed=false在本课堂表示没有业务执行。若模型写true，即使候选列表正确，也拒绝该声明。我们没有召回工具，更没有真实业务回执。

不能反过来说“只要写false就证明系统没副作用”。真实应用需要从执行器、调用轨迹与后端回执确定发生了什么；字段应由可信程序记录，不能让模型自述成为唯一证据。本期纯脚本没有业务动作，才有明确边界。

格式通过与权限通过也不同。未来需要写库存时，应在执行层独立鉴权和审批，不能把“模型JSON通过”变成执行令牌。

## 7. 离线实验与六种预期

环境Python3.11+，无模型、GPU、额外依赖或网络。PowerShell进入仓库根目录：

```powershell
python --version
python llm-zero-to-one/examples/day013_output_acceptance_lab.py
```

文件：[day013_output_acceptance_lab.py](../examples/day013_output_acceptance_lab.py)。源码推导的预期，未执行：

```text
bad_json: parse_error
wrong_type: contract_error
wrong_count: consistency_error
wrong_evidence: evidence_mismatch
false_action: action_claim_rejected
good: accepted_for_human_review_not_execution
```

每次只改一项，用于定位失败发生在哪层。最后一行也没有触发召回，只返回状态字符串。解释器找不到先核环境，文件找不到先核根目录；某案例返回error是预期拒绝路径，不必为了“全绿”删掉错误样例。

## 8. 分段读代码

以下是完整文件片段，不能独立运行：

```python
try: value=json.loads(raw)
except (ValueError, TypeError): return "parse_error"
```

raw是输入文本；loads尝试解析；语法或输入形式不适用时返回解析错误。程序没有把异常吞掉后继续当成功处理。

```python
if value["candidate_count"] != len(rows) or len(set(rows)) != len(rows):
    return "consistency_error"
```

rows是前一步已经确认的字符串列表。set把相同项合并，两个长度不一致说明有重复。先检查类型再做关系判断，可以避免把非法输入带进后续计算。

```python
if set(rows) != EXPECTED: return "evidence_mismatch"
```

EXPECTED是显式给定的合成标准，没有查真实数据库，也没有模型核验。程序把顺序差异忽略，因为本课只关心候选成员；如果业务要求时序排序，验收应另外检查，不能沿用集合比较。

## 9. 常见失败与工程取舍

有的接口JSON响应外面还包Markdown围栏，直接解析会失败；应明确接口契约，不能用删除任意文本的办法把错误悄悄修成成功。结构化输出可减少格式漂移，但要按具体官方接口核查，不把提示中写一句“严格JSON”当保证。

我们的教学解析器还没有处理重复JSON键、深层嵌套/超长输入等完整入口问题；生产入口需明确尺寸、解析策略与数据边界。当前三字段校验也不是通用答案真实性判定器。

当校验失败，要把具体原因反馈给模型并有限纠正；达到预算停止，不能无限重试直到碰巧通过。就算通过，也要把本次检查范围和证据留给人工，不能反复循环给一个空洞“验证成功”。

## 11. 练习与解释性答案

1. n=3、列表[B,B,C]通过吗？**不通过。**重复导致不同批次只有2个。
2. B,C,OTHER数量正确能通过事实验收吗？**本合成标准不能。**证据集合不匹配。
3. 最后一行accepted能自动召回吗？**不能。**只接受到人审，本脚本无执行器。
4. 数量True为什么拒绝？**严格契约要求整数数量，布尔不能充数。**
5. 所有格式检查通过能声称生产验收完成吗？**不能。**还需模型、平台、真实数据和业务范围的实际证据。

当日交付：为一个小任务写字段契约；写一个语法错、一个自洽但事实错、一个伪造动作的输出；分别指出由哪一层拒绝，再写清“通过”只允许走到哪一步。
