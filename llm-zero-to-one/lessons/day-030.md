# Day 030 入门任务卡验收

## 先约定交什么，再看答得怎样

你请同事核对维修工单，同事只回“看起来可以”。想验收这条回复，得先明确工单是哪张、核对哪几份材料、结论如何表示、谁负责最终签字。任务卡把这些约定写在同一处。它像一张明确的交接单，实际软件还要把字段写成程序可检查的数据，并记录执行证据。

本课串起输入、资料、规则、输出、验收和人工责任。目标是能指出一个报告错在格式还是内容，并设计缺证与错误声明的反例。

## 一张完整的最小任务卡

用户为维修文员，痛点是缺资料时反复退回。任务是核对 DEMO-A 工单的 repair、trial 和 return 三份必需材料。输入为带编号的合成观测，repair 和 trial 已通过，return 没有记录，来源编号 demo-01。应输出工单号、准备度、缺证列表和来源列表。人审由维修主管负责，报告状态写成 needs_evidence。

自然语言任务卡进入程序后，可以把应交结果表示为字典，再编码为 JSON。表示形式如下，是实验中的预期值。

```json
{"order_id":"DEMO-A","verdict":"needs_evidence","missing":["return"],"sources":["demo-01"]}
```

这份预期可当作简单的检查基准。基准就是已由人核对、用来比较的参考结果。任务资料改变时，基准也要重新推导。不能把模型自己生成的答案自动当基准。

**小问题**　若只看报告包含来源编号，能证明结论正确吗？

**解释**　还得检查来源里真正记录了什么。脚本第三个报告沿用正确来源编号，却声称可以人审准备完成，还把缺证清空。它会被内容比较拒绝。

## 验收顺序与对照

先检查能不能按输出约定读取，再检查值是否符合当前案例。字段集合或类型错误，结果为 format_error。字段齐全且类型符合，但内容与人工推导不符，结果为 content_error。只有两层都满足本例基准，结果为 accepted。

| 输入报告 | 检查重点 | 预期 |
| --- | --- | --- |
| 与基准一致 | 字段和内容 | accepted |
| 缺 sources 字段 | 字段集合 | format_error |
| 声称准备完成且没有缺证 | 对应资料是否支持 | content_error |

**小问题**　用户把 return 记录补齐且通过，预期值应该如何改？

**解释**　缺证列表可改为空，准备度改为 ready_for_review，来源应增加新记录编号。若仍沿用旧基准，会把合理的新结果误判，验收记录需要绑定资料版本。

## 纸笔推演和课堂脚本

先按表格解释三个结果，再准备 Python 3.11 或更新版本。从仓库根目录运行 [完整脚本](../examples/day030_task_card_lab.py)。

```powershell
python llm-zero-to-one/examples/day030_task_card_lab.py
```

脚本构造三份报告，调用 check_report，先用字段集合和类型校验排除格式错误，再比较字典内容。最后每条打印一个 JSON 结果。预期输出如下，当前只静态检查和手推。

```text
{"case": "normal", "check": "accepted"}
{"case": "missing_field", "check": "format_error"}
{"case": "unsupported_claim", "check": "content_error"}
```

若出现文件不存在，先检查当前目录。若缺字段仍报 accepted，查字段集合是否被改成只检查其中一个。脚本采用完全相等的固定答案，列表顺序也参与比较。开放问题允许不同表述时，需要按声明的规则比较集合、数值或证据支持，并另行检查文字陈述。本实验是脚本报告的验收设计，模型实机结果需要单独留证。

## 任务卡怎样接上 Agent

模型接收任务卡和可用工具说明，选工具和参数；程序验证并执行；结果加入下一轮输入；模型继续选择或提交报告。对应维修结案 Agent，验收要看它是否拿到必需清单、读取证据并保留失败和缺证，而不能只看最后一句建议。给循环设轮数上限、超时和失败响应后，还能测试它在坏参数、无证据和超限时是否正确停止。

当日交付是一张任务卡、三类检查表和一个自己新增的反例。参考答案可把工单号改成 DEMO-B，其他字段保持相同。格式仍正确，但不符合当前工单，因此 content_error。编号和来源范围约束了报告实际回答哪个问题。
