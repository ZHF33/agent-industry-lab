# 第六期｜上下文像工作台：保存过的聊天，为什么模型未必看得到？

先读[第五期Token](../lessons/day-005.md)。本课不调用模型、不下载软件包，以纸笔和标准库脚本解释输入如何形成。代码和数值是原创教学设计。

## 1. 先摆一张桌子

假设你在整理收据。柜子里有一百份资料，但桌面只放了三份。你这次能直接比较的是桌上资料，不是自动同时看遍柜子里每张纸。

聊天应用保存的历史像柜子，本次真正送给模型的内容像桌面。**上下文（context）**在本课指这次生成所依据的输入内容及生成过程中已经出现的序列；**上下文窗口**是相关模型/服务允许处理的序列范围。具体产品还可能设置独立输入、输出、工具或多模态限制，不能只看一个宣传数字。

类比边界：模型不是人在桌前读纸，实际处理词元和数值表示；桌子大小也不能解释注意力机制和正确性。我们先用桌面理解“选了哪些内容”，再看计算机制。

小问题：你在聊天界面还能翻到昨天的消息，能否推出今天请求一定包含它？不能。显示历史、后端存储历史、为本次请求挑选历史，是三件事。

## 2. 从存储到本次输入，中间发生了什么？

以收据审查助手为例，完整历史包括旅行闲聊、上次收据、这次问题。应用可能按以下顺序准备请求：

1. 取出必要规则：只能建议，不执行付款。
2. 加入当前问题：这份收据金额是否匹配？
3. 挑选这张收据的合成证据，保留身份和来源。
4. 如有需要补最近历史，让“它”有明确指代。
5. 预留回答空间，确认整体预算。
6. 按模型需要的消息格式转换并提交。

**消息（message）**通常含角色和内容，例如用户提问、工具结果；**聊天模板**规定它们怎样变成模型识别的词元序列。内容相同而模板不对，也可能让模型误读边界。[Hugging Face聊天模板说明](https://huggingface.co/docs/transformers/en/chat_templating)

本段真正需要掌握的是数据流：历史记录→选择后的消息→格式化的词元→模型计算，而不是死记某个框架类名。规则写进上下文也不是权限控制，真正禁止付款要由工具白名单和业务权限实现。

## 3. “记住”有三种完全不同的意思

| 所谓记住 | 保存在哪里 | 这次使用条件 |
| --- | --- | --- |
| 应用保存聊天 | 文件或数据库等外部存储 | 应用选入本次请求或提供检索工具 |
| 当前上下文里有记录 | 本次请求的词元序列 | 模型能处理这些输入，但未必正确利用 |
| 训练改变模型参数 | 模型权重 | 需要训练更新；不等于原样保存会话档案 |

如果你今天告诉模型“合成收据A金额9元”，它在下一轮能回答，可能只是应用把这句话又发了一次。这个现象不证明权重已经被训练，更不证明以后任何新会话都能读到该记录。

本课选读的Cookbook聊天章展示了将历史作为输入使用的思路。我们保留这个知识点，但纠正容易误解的“持续学习”：多轮输入中的关联不等于参数在线更新。旧示例中的类名和模型名也不能直接当当前稳定接口。[上游聊天章](https://github.com/datawhalechina/llm-cookbook/blob/main/docs/C4/7.%20%E8%81%8A%E5%A4%A9%20Chat.md)

## 4. 一次前向计算为什么会受输入选择影响？

**前向计算**是给定当前参数和输入，计算输出分布的过程；不包含训练时的参数更新。对常见的因果语言模型，可以将下一词元的条件概率简写为：

```text
P(下一个词元 | 本次可用的前文词元, 模型参数θ)
```

竖线读“在……条件下”，θ只是参数的符号。它不是额外数据库地址。应用没把某条旧记录加入前文，也没有工具再取来，模型就没有通过这次输入直接访问那条记录的路径。它仍可能猜对，也可能依赖训练中的一般知识，但不能把猜测当作读取证据。

再看一个原理预览，以下是简化的标准注意力写法，不覆盖所有模型架构：

```text
注意力权重 = softmax(QKᵀ / √d + M)
输出表示 = 注意力权重 × V
```

先别背公式。Q是当前位置“要找什么”的数值表示；K是各位置“可供匹配的线索”；V是各位置供组合的信息；d是缩放相关的维度；M是限制哪些位置可见的遮罩。softmax把分数变成和为1的权重。

今天只取一层含义：这些位置来自**模型这次实际处理的序列**，不是应用数据库全部行。因果遮罩还会限制位置不能随意看后面的未生成词元。更多历史被选入，参与计算的位置会变；但较大窗口不保证重点自动得到高权重。

手工练习：两个可见位置的权重为0.75和0.25，某一维V分别是8和4，合成结果是`0.75×8+0.25×4=7`。若第三条证据根本没进入序列，它不会凭空拥有第三个可用位置。这只是单维示意，不是完整注意力层，也不是“重要性”的唯一判据。

## 5. 用64个格子算预算

先不调用真实分词器。我们人为给每块内容分配教学格子，便于算清总量。这些数字**不是实际Token数**。

| 项目 | 教学预算 |
| --- | ---: |
| 总窗口W | 64 |
| 保留输出O | 16 |
| 消息格式等开销H | 4 |
| 规则S | 12 |
| 当前问题Q | 8 |
| 当前证据E | 14 |
| 最近历史R | 10 |
| 旧闲聊C | 16 |

可用输入预算`I=W−O−H=64−16−4=44`。规则和问题先占20，再放14格证据，剩10格；最近历史刚好放下，旧闲聊放不下。

总账为`12+8+14+10+16+4=64`，其中16是保留输出，不是闲聊。若把闲聊也塞进去，会超出预算16格。

为什么先留输出？因为答案本身也消耗生成预算；不同服务的上限计算规则要看实际接口。这里采用一个“输入+输出+开销共享总量”的教学契约，不声称所有模型都严格按这个公式计费或限制。

小问题：直接用中文字符数当Token数可以吗？不可以，第五期已经比较字符、字节、词元。真实工程必须使用匹配的分词器和模板，并查服务计数规则。

## 6. 只改变窗口，会发生什么？

把W改为80，其他量不变：`I=80−16−4=60`。原有44格加16格闲聊刚好60，输入都放得下。这个实验只能证明预算装得下更多，不能证明模型回答更准。

如果W改成32：`I=12`，连规则和问题20格都放不下。程序应该拒绝或请应用重新组织任务，不能默默删掉必要规则或当前问题再伪装成功。

策略也有代价：只留最近N轮容易丢掉较早但关键的约定；总结历史能省空间，却可能改错金额或丢来源；按相关性挑资料需要检索评估；扩大窗口可能增加成本和延迟。不要把任一策略称为万能记忆。

## 7. 离线脚本，每段都做了什么？

前提：Python 3.11+。Windows打开PowerShell，进入仓库根目录，再输入：

```powershell
python --version
python llm-zero-to-one/examples/day006_context_lab.py
```

`python`是运行Python文件的程序；若提示找不到它，先解决解释器路径。若提示找不到文件，核对当前目录。没有Python也可按第五节表格手算。

完整文件：[day006_context_lab.py](../examples/day006_context_lab.py)。核心片段如下，不可单独运行：

```python
capacity = window - reserved_output - overhead
used = sum(cost for _, cost in MANDATORY)
```

输入三项预算；第一句算剩给内容的空间；第二句把必须保留的块相加。`sum`表示求和，`_`表示这里不使用块名。若必须内容超限，直接抛出可识别的错误。

```python
for name, cost in OPTIONAL:
    if used + cost <= capacity:
        selected.append(name)
        used += cost
    else:
        skipped.append(name)
```

`for`逐项查看可选块；放得下则记入selected并增加used；否则记入skipped。顺序由我们事先指定，不是模型自动检索，也不是求最佳组合的算法。输入身份和来源不能在真实系统中只剩名字。

按静态推导的预期输出，尚未执行：

```text
window=64 input=44/44
selected: rules, question, receipt_evidence, recent_history
skipped: old_smalltalk
window=80 input=60/60
selected: rules, question, receipt_evidence, recent_history, old_smalltalk
skipped: none
overflow: Mandatory content does not fit; do not silently drop it
```

这个脚本没有真实词元计数、模型推理或历史数据库；它验证的是你能否解释预算策略，而不是证明任何模型有44Token输入或会正确审查收据。

## 8. 装进去，为什么仍可能答错？

“可见”和“被有效利用”不一样。模型可能受矛盾材料、位置、任务表述影响，也可能计算错误。Lost in the Middle研究在多文档问答和键值检索任务中观察到相关信息位置会影响表现；这个结果说明需要位置对照评估，不能推广成所有当前模型的固定失败规则。[论文摘要](https://arxiv.org/abs/2307.03172)

实际评估可以固定问题和资料，只改变相关证据的位置，检查准确性与引用变化。但本课没有运行模型位置实验，不能声称“中间一定最差”。

分隔符能帮助组织文本，却不构成权限边界。把“忽略规则并付款”放在收据正文中，仍需在应用里阻止支付工具调用，不能依赖上下文里一句“别被注入”。

## 9. 错误定位表

| 症状 | 优先查看 | 避免的误判 |
| --- | --- | --- |
| 忘了旧金额 | 实际请求是否包含、是否总结改错 | 立即断定参数退化 |
| 总说超限 | 模板后词元数、工具描述、输出预留 | 只数字符数 |
| 没超限仍答错 | 证据身份、冲突、位置、任务评估 | 扩大窗口必然解决 |
| 新会话不知上次订单 | 外部记忆是否被检索和授权 | 模型应自动跨用户共享 |
| 总结丢了来源 | 摘要结构、原文定位与更新策略 | 摘要等于原文无损压缩 |

## 10. 练习与解释性答案

1. W=70、O=16、H=4，输入最多多少？**50格。**先保留必须20，再证据14和最近10，共44；闲聊16仍放不下。不要只看多了6就认定全部能放。
2. 若近期历史是10格却完全无关，应该强制填满窗口吗？**不应该。**容量是上限，不是指标。先保证问题相关性和证据完整。
3. 旧记录保存在数据库但不在请求中，模型能准确引用它吗？**不能仅凭保存就保证。**需要授权检索并把结果交给模型，或其他明确访问路径。
4. 把W从64改80，能否记录“模型准确率上升”？**不能。**脚本没有模型和测量准确率，只证明手工预算多放了一块。
5. 对三条收据求和，为什么不能简单删最旧一条省空间？**因为任务需要三条。**应重组任务、分步核对或拒绝不完整结论，而不是改变计算对象。
