# Day 028 JSON 交换格式

仓库甲系统把电量写成一张可交接的单据，乙系统按约定读出“wh 是整数，以瓦时计”。两边可用不同软件，交接文本需遵守同一格式。JSON 是一种用文本表达对象、数组和基本值的格式。它像通用表单，但只能说明如何表达数据，字段单位和范围仍由业务约定。学完能区分格式错误、字段不合约定、可继续处理三种结果。

## 从字面符号到程序里的值

在 {"wh": 500} 中，花括号表示对象，双引号中的 wh 是名字，冒号将名字和值连起来。值 500 在 JSON 中是数字。解析是按格式规则读文本并生成程序对象。在本课的 Python 环境中，json.loads 将整个对象读成字典，500 读成整数。可通过 record["wh"] 取值。若同一数字加双引号，变成 "500"，解析仍成功，但得到字符串。字符串是字符序列，即使外观看来像数字，也可能是标识码或显示文字。业务契约需要明确接收哪一种。

**小问题**　输入 {"wh": "500"} 会落到语法错误吗？

**解释**　不会，字符串是合法 JSON 值。它不能满足本课只接收非负整数的契约，故属于业务字段错误。程序也不会把它擅自转换成数字。

## 用三份资料走一遍

下方是完整脚本中的解析片段，需要通过实验命令运行完整脚本。

```python
try:
    record = json.loads(raw)
except json.JSONDecodeError:
    return {"status": "syntax_error"}
```

先解析，失败时记录语法状态。下一段检查解析结果是不是字典，再检查 wh 的确是非负整数。脚本使用精确类型检查，使 JSON 中的 true 也不能充当一瓦时。验证通过后把状态和数值放回字典。最后 json.dumps 把字典编码成 JSON 文本，便于另一段程序读出。

| 输入 | 解析后 | 返回状态 |
| --- | --- | --- |
| {"wh": 500} | 字典，值是整数 500 | accepted |
| {"wh": "500"} | 字典，值是字符串 "500" | contract_error |
| {"wh": 500,} | 结尾逗号无法解析 | syntax_error |

**小问题**　只从第三条移除逗号，预期怎样变化？

**解释**　文本变得与第一条等价，字典中的值仍是整数 500，最终得到 accepted。若语法修好后仍得到 contract_error，应查字段名、值类型以及字段是否存在。

## 实验与验收

准备 Python 3.11 或更新版本。打开终端进入仓库根目录，运行 [完整示例](../examples/day028_json_exchange_lab.py)。使用标准库，无需模型。

```powershell
python llm-zero-to-one/examples/day028_json_exchange_lab.py
```

预期输出如下。本次只做静态检查和手工推演。

```text
{"status": "accepted", "wh": 500}
{"status": "contract_error"}
{"status": "syntax_error"}
```

若无法打开文件，先检查终端目录。若把 outputs 当作 Python 字典直接打印，通常会看到单引号，调用方不能假定这就是 JSON。若对有效输入得到 contract_error，检查字段名是否改了大小写。提交验收表时再加入 {"wh": 0} 和 {}。前者是有效的零电量，后者没有电量字段，应退回。这也解释了为什么缺字段不能由接收方补零。

实际 Agent 需要进一步确认电表身份、数据时点和档位。在处理外部证据时，还需决定如何拒绝重复字段。格式合法只使双方能交换值，业务校验决定这些值能否用于复核。
