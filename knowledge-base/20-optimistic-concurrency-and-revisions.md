# 第二十讲｜刚批准的修改，为什么提交时还得检查版本？乐观并发与丢失更新

对应[工单修订冲突审查Agent](../examples/revision-conflict-review/README.md)。只做内存示意，不修改工单、不接数据库。

## 1. 两个人，读到同一张工单

工单revision=4，优先级normal。甲、乙几乎同时打开。甲把优先级降为low，已经保存为revision=5；乙仍拿着旧页面，想升为high。如果乙直接覆盖，甲的修改就可能被无声抹掉。

这叫**丢失更新（lost update）**：一个基于旧状态的写入覆盖了他人的已完成修改，系统没明确处理竞争。谁的判断正确需要业务复核，不能因为谁后点按钮就自动认定谁对。

类比两人拿到同一版纸质表格，各自修改再交回。先看表格版号，发现不同就停下来核对。类比边界：真实系统有并发、网络、事务和多资源规则；纸上版号不能解释所有数据库隔离问题。

小问题：页面只打开十秒，能当成最新吗？不能。十秒内也可能有人修改；新鲜度与版本前提是不同证据。

## 2. 为什么“先看一眼没变，再写”仍不够？

按时间列出一个反例：

| 时刻 | 乙 | 甲 |
| --- | --- | --- |
| t1 | 读取revision=4 | 读取revision=4 |
| t2 | 再查仍是4 |  |
| t3 |  | 写入low，变5 |
| t4 | 无条件写入high | 修改被覆盖 |

乙在t2检查正确，不代表t4仍适用。**检查与使用之间的时间窗口**会让先前结论失效。人工审核也有同样问题：批准的是当时看到的对象、提案和版本，不能无限期给未来状态授权。

解决方向是让真正持有记录的系统在执行处同时判断版本条件和修改，失败时不覆盖。这叫**原子操作**：相关步骤在竞争者眼里作为不可分割的一个操作完成。不是简单把两行Python写在一起。

## 3. 乐观并发，乐观在哪里？

**乐观并发控制**通常先允许读取与准备提案，不一直占着排他锁；到了提交阶段，用版本条件检查期间是否发生冲突。发生冲突就拒绝或重新核对，而非静默覆盖。

本课用最小契约：

```text
如果当前revision == 提案base_revision：按规则修改并生成新revision
否则：保持原记录，返回冲突
```

**比较并交换（CAS，compare-and-swap）**可先理解为“比对预期值，符合才替换”。它需要执行端保证原子性。本课的内存函数只展示这个输入输出契约，没有多线程/多机原子保证。

这里版本必须对每次受保护的修改更新，不复用旧版本号。否则内容改走又改回而版号复用，会丢失“中途变化过”的信息。版本号是对象范围内的约定，不是跨所有系统通用的时间。

## 4. 手推三次提交

从revision=4、priority=normal开始：

1. 甲提交expected=4、priority=low。匹配，得到revision=5、low。
2. 乙提交expected=4、priority=high。不匹配，保持revision=5、low。
3. 乙重读5，重新评估并获适用授权后，提交expected=5、high。若期间无其他变化，得到6、high。

第三步不能简化成“出冲突就自动把expected改成最新再重发”。这会绕过重新阅读与审查，把防覆盖机制变回最后写者胜。是否能合并、能否自动重试，要由业务含义决定。

小问题：如果甲改负责人、乙改优先级，是否必然可以合并？不必然。字段不同仍可能有跨字段规则，例如负责人所在队列限制优先级。需要明确合并策略与校验。

## 5. 数据库写入应该怎样表达条件？

以下只是设计示意，不可独立运行，也不在本课执行：

```sql
UPDATE work_order
SET priority = :new_priority, revision = revision + 1
WHERE id = :record_id AND revision = :expected_revision;
```

`WHERE`把对象身份和预期版本放在同一次更新条件中。参数应由数据库驱动绑定，不能用用户文本拼SQL。执行端检查影响行数：0表示没有匹配更新，可能是版本变了、对象不存在或权限视图等原因，须按业务接口判断；不能一律声称“别人刚改了”。

生产还需要可信身份、租户条件、合法字段与业务状态、事务、错误处理和审计。PostgreSQL文档说明并发更新时会依据规则处理目标行及重新评估条件；这里不是说一条SQL能解决所有隔离与多对象一致性。[官方事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)

第1讲关注事务、幂等与重试，第3讲关注状态和审批；今天专讲“旧提案能否应用到当前版本”。幂等键阻止同一请求重复，并不自动发现两个不同请求基于同一旧版本。

## 6. HTTP里的类似思路：If-Match

**HTTP**是常见的网络请求/响应约定。**ETag（实体标签）**是服务端提供的表示版本验证信息，通常按接口约定作为不透明标识使用，不应自行拆解成可比较大小的序号。

`If-Match`把“我期望的表示仍匹配”作为请求前提。RFC 9110要求该条件使用强比较；带`W/`的弱标签不能当作相同强标签匹配。前提不满足通常返回412，具体协议还规定相关例外和前提顺序。[RFC 9110 §13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match)

本课仅用整数revision讲原理，不声称整数就是完整ETag实现；Agent API没有实现If-Match。把HTTP头放进去但服务器忽略条件，也没有防止覆盖。授权检查与版本条件都要有效，版本匹配不是权限证明。


True/False分别表示模拟条件是否通过；不是人工审批是否真的完成。代码第三次调用由我们编写，名称re-reviewed只是场景假设，不是系统保存了真实审批证据。

## 8. 代码输入、动作、输出

以下是完整文件片段，不能单独运行：

```python
if record["revision"] != expected:
    return False, dict(record)
```

输入是当前内存记录与期望版号。`!=`表示不相等；冲突时返回False及原值复制，没有把priority写进去。

```python
return True, {"revision": expected+1, "priority": priority}
```

条件相同则构造新字典，版号加一。返回的是新值；没有网络、数据库和多机竞争。这个函数的“比较后构造”在本演示里按顺序调用；真实共享状态需要存储层或同步机制提供原子性。

如果程序找不到python先查解释器路径；找不到脚本查当前目录；显示B stale: False正是预期冲突，不应当作需要关闭检查的故障。

## 9. 与今日Agent的真实边界

三个工具读取提案、当前快照并比较。样例基准4、观察5，输出revision_conflict；缺基准、陈旧证据、身份错配、关闭记录分别表达。

工具没有执行真正的CAS。approve只接受“需重读重审”的建议，不编辑工单、不派单。即使结果matching_snapshot_requires_review，也不能跨过真正提交时的版本条件。

生产接入优先补写端条件、租户身份、审批绑定与审计，再考虑队列重试等能力。结构化版号检查不需要RAG或向量库；模型负责解释报告，不能决定跳过版本条件。

## 10. 故障与取舍

| 现象 | 原因方向 | 正确处理方向 |
| --- | --- | --- |
| 总被人覆盖 | 无条件更新、版本不递增 | 审提交契约与原子条件 |
| 冲突后自动成功 | 客户端擅自换expected | 重读与重新授权，别绕过条件 |
| 同版本却越权 | 版本当权限 | 独立身份/租户/字段授权 |
| 已批准但写失败 | 审批后有新修订 | 检查批准绑定的版本与新状态 |
| 影响行数0 | 多种未匹配原因 | 区分不存在、范围与冲突 |
| 冲突率高 | 热点对象频繁改 | 评估锁、任务串行化或业务拆分 |

乐观方式减少长期占锁，但冲突多时可能反复返工；悲观锁先占资源有另一组吞吐和等待代价。选择取决于冲突率、操作时长和业务规则，不是“乐观一定更先进”。

## 11. 练习与解释性答案

1. 两人都读7，甲写成8，乙expected=7会怎样？**拒绝，保持8。**必须由真正执行端落实条件。
2. 时间戳都在一分钟内，能忽略版本差异吗？**不能。**短时间仍可修改，时效与身份/版本是不同维度。
3. approval=true能代替CAS吗？**不能。**人批准以后记录仍可能改变。
4. 冲突后只把expected改8就重发，安全吗？**不自动安全。**旧提案可能不适用，须重读、重算和必要重审。
5. 本例是否验证数据库并发正确？**没有。**它只展示顺序内存契约，没有连接数据库或并发压力实验。
