# 第五讲：同样写着12点，为什么Agent会算错延误？

配合物流延误调查Agent，讲清时间、时区和观测快照。

## 1. 从两块墙钟开始

纽约同事说“早上8点”，另一位同事说“中午12点”。两个人可能说的是同一瞬间，也可能不是。只看到8和12就相减，会把没有发生的4小时延误算出来。

程序需要的不只是钟面数字，还需要日期和与统一时间的关系。**UTC**是一种统一时间基准；**偏移**说明当地钟比UTC快或慢多少。例如 `08:00-04:00` 表示该钟比UTC慢4小时，对应 `12:00+00:00`。这里给的是明确偏移，不是把纽约全年固定为-04:00；实际地区规则可能随夏令时改变。

类比边界：墙钟只显示时间，业务记录还要日期，否则昨天12点与今天12点会被混淆。固定偏移也不能描述地区未来的完整时区规则。

小问题：记录“12点送达”够不够？答案：不够，至少要日期、时间及明确时区，且要知道它是承诺时间还是实际送达时间。

## 2. 一条运单至少有三种时间

**ETA**是预计或承诺送达时间，取决于上游契约，不能只看字段名猜法律或业务含义。**事件时间**是扫描或签收发生的时间。**观测时间**是“我们现在站在哪个时间点分析”。本案例用固定as_of表示观测快照，不读取运行电脑的当前时间。

假设ETA12点，我们在13点分析，最新扫描10点。能说“超过承诺时间1小时，签收信息待确认”；不能说“肯定还没送达”，因为可能送达了但记录没上传；也不能说“枢纽扫描导致延误”，扫描只是事件，并不证明因果。

这是数据与状态基建的一部分：时间口径决定查询哪些记录、如何计算结果、能否复现。它不只是网页格式化日期。

小问题：收到一条14点的扫描，可以用来解释13点快照吗？答案：不能把未来发生的事件当成13点已经知道的证据。可以保留原始记录，但评估需排除。

## 3. 有时区和没时区，程序分别知道什么？

Python的datetime表示日期和时间。有时区信息的对象称为aware；没有时区信息的对象称为naive。中文可以理解为“知道相对UTC位置”与“不知道”。不知道并不自动意味着UTC，也不自动意味着当前电脑当地时间。

概念片段，不能独立运行：

```python
moment = datetime.fromisoformat(value)
if moment.tzinfo is None or moment.utcoffset() is None:
    raise ValueError("Timezone is required")
```

输入是时间字符串；fromisoformat按支持的ISO格式解析；随后检查是否有可用时区。缺少时区就拒绝。这样会让某些数据不能直接进入流程，但比悄悄猜一个时区更可追踪。真实业务可约定缺省时区，但必须写入数据契约，并保留转换记录。

本仓库utc_time函数名表示进入统一时间比较链，并不把显示文本全部改写为UTC；返回仍可携带原偏移。datetime比较能理解明确偏移，同一瞬间的两个表示可以相等。

## 4. 时间差怎样计算？

```python
delta = observation - eta
seconds = delta.total_seconds()
minutes = int(max(0, seconds) // 60)
```

第一步相减得到timedelta，意思是一段时间长度。第二步拿到整个间隔的秒数。第三步负值归零，再换成整分钟并向下取整。千万不要把delta.seconds当整个间隔，因为它不是包含天数的完整总秒数。

超过12点30秒，整分钟会显示0，但“已经逾期”仍可能成立。项目判断状态使用原始秒数，显示使用整分钟，两者用途不同。负差表示尚未到ETA，不应输出负延误。

如果有明确签收时间，就用签收时间减ETA衡量实际迟到；没有签收证据，用观测时间评估“截至快照已超时”。签收时间晚于快照属于输入矛盾，程序拒绝，不能假装在13点已经知道14点签收。

## 5. 为什么固定快照比电脑时钟适合示例？

同一个样例今天运行和明天运行，如果每次直接使用now，结果会变。初学者不知道是代码变了还是时间变了。固定快照让相同输入得到相同评估，便于比较程序修改前后。

生产系统当然可以使用实时观测时间，但应把它作为一次任务的明确输入或保存字段。恢复人工审批时不要重新取now替换旧快照，否则主管审核的建议与后来记录的建议不属于同一时间基础。

例子的as_of是业务观察时点，不是日志输出时间，也不是n8n收到HTTP请求的时间。这三种时间混在一起，会让延误报告不可解释。

## 7. 常见故障与边界

时间差固定多几小时：检查是否把本地时间误当UTC。到夏令时突然偏一小时：检查是否用一个固定偏移代表全年地区规则。跨天后结果只剩几分钟：检查用了seconds还是total_seconds。显示0分钟却标超时：检查是否不足一分钟，不要立刻认为程序矛盾。

旧报告变化：检查恢复任务是否用了新的now。历史调查用了未来轨迹：检查事件筛选与快照。缺签收直接判未送达：检查把“没证据”与“证实没发生”混淆没有。

工程取舍：当前项目接受带明确偏移的时间，计算使用标准库，不必为了三条合成记录增加时区服务。真实多地区系统需要地区时区规则、输入来源与数据契约；轨迹还可能同时包含发生时间和系统收到时间。要按“当时系统知道什么”复盘，需要收到时间，而不仅是发生时间。本例只有事件发生时间，不能宣称已经实现历史知识完整回放。

## 8. 练习与解释性答案

一：UTC12点与08点-04:00相差4小时吗？不是，同一日期下它们是同一瞬间。

二：模型看到“枢纽扫描”可以写“枢纽积压导致延误”吗？不能，原因需要额外证据，工具明确输出unknown。

三：主管一天后审核，应该把逾期自动改成25小时吗？不应默默改。审核的是原快照调查；若需最新评估，应明确产生新快照并让主管看新证据。

四：HTTP请求时间能代替签收时间吗？不能，收到请求与实际签收不是同一事件。

五：晚于快照的签收能用于那个快照的结论吗？不能。应拒绝矛盾输入或明确产生新快照，不能靠模型解释掉。
