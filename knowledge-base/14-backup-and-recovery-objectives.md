# 第十四讲｜备份不是恢复：怎样定义“丢多少”和“多久恢复”？

零基础，不启动数据库、不创建备份、不覆盖任何文件。配套[备份恢复证据复核Agent](../examples/backup-recovery-review/README.md)。

## 1. 一个看起来全绿的订单系统

合成订单服务的备份在13:00显示“成功”。13:04有人问：“假设现在故障，能恢复到哪里？多久能让店员继续接单？”负责人打开历史演练记录：上个月用过一份旧备份，22分钟恢复服务。

这还不足以回答今天的问题。13:00是备份完成时间，不必然代表其中有截至13:00的全部订单；上月恢复过旧备份，也不证明今天的新备份能恢复。任务成功、数据覆盖、恢复过程和业务验收必须分开。

生活类比是手机照片：云端显示上传完成，不代表最近十分钟新拍的照片都已上传；下载了一张压缩包，也不代表每张照片能打开。类比只解释“保存与可使用不同”，数据库还要处理多条记录之间的一致性，比照片复杂。

今天交付两张时间线：一张标出可能丢失的数据区间，一张标出服务恢复的耗时。不要只写“已备份，安全”。

## 2. 先解释四个最小概念

**备份**是保留可用于恢复的资料副本或恢复所需材料。**恢复**是利用这些材料，把系统带回可使用状态的过程。**恢复点**表示资料能够覆盖到哪个业务时刻。**一致性**表示恢复出来的数据关系符合系统规则，而不是每个文件看起来都存在就算合格。

假设一笔订单包括“订单已创建”和“库存已扣减”。如果恢复后只有前者，没有后者，就可能得到不符合业务约定的组合。真实数据库怎样维持这种关系，要结合事务、日志和备份方法；不能随意复制正在变化的文件就宣称一致备份。

本课先理解目标和证据，不要求实现数据库内部恢复机制。到后面的实战再针对明确版本选择工具和验证方法。

小问题：备份文件大小和昨天差不多，是否证明里面的订单齐全？**不能。** 大小只是一项属性，不证明记录覆盖与关系正确。

## 3. RPO：允许丢失多靠近故障时刻的数据？

**RPO，恢复点目标**，用于表达可接受的数据损失时间范围。假设业务接受最多15分钟的数据损失，它不是在说“备份程序必须15分钟跑完”，而是希望故障时有足够新的可用恢复点。

合成例子：

```text
12:50 可恢复数据的记录时间点
       └──────── 14分钟 ────────┐
13:00 备份任务完成             │
13:04 假设故障/评估参考时刻 ◀───┘
```

纸笔计算：13:04减12:50是14分钟，即840秒。如果恢复点确实可用、时间口径正确，单看这个时间间隔，它没有超过15分钟目标。但本例只是清单里的恢复点声明，尚未验证备份链和实际恢复，因此代码称为recorded_point_within_target，不叫“实际RPO验收通过”。

若错误地用13:00完成时间，算出来只有4分钟，会低估可能丢失的区间。这是本课最重要的反例。

RPO是目标，实际可恢复数据损失是测量结果。真实事务提交、系统间复制、可用日志范围和故障时刻都可能影响判断；不能只看定时任务的运行频率推定达标。

## 4. RTO：业务最多可以等多久？

**RTO，恢复时间目标**，表达中断后到业务恢复可接受状态所允许的时间。它与丢多少数据是两个维度。

先明确起止点，否则两个“恢复耗时”不能比较：有的记录从开始导入算到数据库启动；业务可能要求从事故发生算到店员能够完成一笔订单。发现故障、授权、资源准备、数据恢复和业务检查的耗时，可能都需要计入。

本例演练的started_at明确表示模拟业务中断开始，service_ready_at明确表示完成约定检查、服务恢复可用。12:00→12:22是22分钟，小于本例30分钟目标。它只是那次合成演练的记录，不能推定今天也一定22分钟。

```text
演练中断开始 → 准备环境 → 恢复数据 → 服务启动 → 业务检查完成
12:00                                               12:22
```

小问题：数据库进程两分钟就启动了，是否RTO就是两分钟？**不一定。** 若业务还不能正确读写，目标终点尚未到达。必须说明口径。

## 5. 两个目标为什么不能合成一个“健康分数”？

| 情形 | 恢复点很新吗？ | 恢复服务很快吗？ | 不能省略的事实 |
| --- | --- | --- | --- |
| A | 是 | 否 | 数据少丢，但业务可能等很久 |
| B | 否 | 是 | 很快恢复了较旧状态，仍可能丢很多新订单 |
| C | 是 | 是 | 还要证明备份可用、业务检查有效、证据适用当前环境 |
| D | 无法判断 | 无法判断 | 缺证据不能当作0风险，也不能直接等同已失败 |

RPO与RTO应由业务与技术负责人一起确定，并明确范围和测量口径。15/30分钟只是本课程示例，不能当作所有行业的统一要求。

## 6. 备份方法先建立地图

常见思路包括逻辑导出、文件或物理层备份、基础备份结合连续日志等。它们的速度、恢复粒度、环境依赖和运维成本不同。这里是技术地图，不是针对任何数据库直接可执行的命令。

以PostgreSQL文档为例，日志归档和基础备份可以组成时间点恢复所需材料。**时间点恢复（PITR）**先理解为在具备合适材料与完整链条的条件下，恢复到指定时间附近的目标状态。不能只有日志就默认足够，也不能把“我有一个最新文件”当作完整恢复方案。

为什么缺一段材料可能出问题？类比解题：如果最后一步依赖中间结果，中间结果丢失，最后一张纸不能自动补回。实际日志恢复是数据库定义的过程，不是随意拼文件。选定数据库、版本、备份工具与流程后，需要按其官方文档验证。

本课不提供会覆盖数据目录的操作，避免把概念课误当成生产恢复指南。

## 7. 从清单到可恢复，需要哪些证据？

1. **对象身份**：系统、备份编号、版本和范围是否对应。
2. **时间覆盖**：恢复点是哪一时刻，记录是否新鲜，有无未来或倒置时间。
3. **材料可用**：所需文件、日志、密钥和访问权限是否可用；哈希仅说明与某基准字节是否一致。
4. **隔离演练**：在获准环境按方案实际恢复，记录环境、开始与结束。
5. **业务验收**：对关键记录、关联约束和必要业务动作做合成或获准检查。

不应把真实客户资料公开做教学证据。本仓库只用合成元数据，不带真实备份、数据库或解密密钥。

“哈希相同”不是“可恢复”：一个本来就不完整的备份复制后哈希仍可相同；缺解密材料也可能让完整字节无法使用。前面哈希课程讲完整性，本课增加恢复过程与业务有效性这层判断。

## 8. 代码怎样表达这些区别？

配套[recovery_lab.py](examples/recovery_lab.py)复用新Agent的assess工具。它只计算合成记录，不执行备份或恢复。

核心三步可以先纸笔理解；下面是不可独立运行的摘录，完整例子在链接中：

```python
reference = instant(as_of)
point = instant(record["recovery_point_at"])
lag = (reference - point).total_seconds()
```

输入是参考时间与恢复点文字；instant检查UTC偏移并转成统一时区；相减得到时间间隔，再换算成秒。没有把数据文件送给模型。

工具还检查point≤completed≤observed，以及演练started≤ready≤observed。时间线矛盾或证据来自参考时间之后，直接拒绝，不把矛盾数据强行做出一个好看的结论。

第二层是证据前提：备份状态不是completed或清单太旧，RPO证据为insufficient_evidence。演练不是passed，历史RTO也不能判within_target。然后独立列出演练陈旧、未测试最新备份和缺少哈希记录等缺项。

**insufficient_evidence**意思是现有记录不足以支持判断，不是说真实世界一定成功或失败。actual_recoverability始终unknown，因为这个函数没有做实际恢复。

## 10. 常见故障与工程取舍

- `Timezone required`：时间没有偏移。补上真实口径，不要直接随手加UTC冒充准确时间。
- `Inconsistent backup timeline`：恢复点、完成与观察顺序矛盾。先查资料来源和字段含义，不能把异常吞掉后显示绿色。
- `Future evidence`：证据时间晚于参考时间；可能时钟或参数错误，先核对，不用未来记录证明过去状态。
- `ModuleNotFoundError: agent`：完整目录缺失，检查示例相对位置；不要随便安装同名包。

真正接入业务时，备份平台适合负责操作和权威清单，受控适配器提供最少元数据，Agent负责跨记录复核与解释。把数据库恢复动作直接暴露给一个自由文本工具，不是本课的方案。人工批准建议与真正执行恢复应有不同权限和流程。

当前演示的LangGraph检查点自己还只在内存里，重启会丢失。研究“备份”主题不等于这个Agent已经拥有持久灾备；要把主题能力与实际实现分开记。

## 11. 练习与解释性答案

**一：13:00备份完成，恢复点12:50，13:04故障，可能丢失窗口用4还是14分钟？** 按给定恢复点计算为14分钟，完成时间不等于数据覆盖终点；实际可用性还需验证。

**二：演练22分钟完成，目标30分钟，能断言今天达标吗？** 不能。它是历史样本，环境、数据量、版本和操作条件可能变化，当前演练证据还已陈旧。

**三：清单很新且哈希匹配，为什么还要演练？** 因为完整字节不证明材料能被正确解密、组合、恢复和用于业务。

**四：把目标从15分钟改成30分钟，真实数据会变新吗？** 不会。只改变判定标准，资料与系统能力没有随之改善。修改目标需要业务认可，不能为了变绿随意放宽。

**五：将模型换得更大，能代替恢复工具吗？** 不能。模型可以组织解释，但缺少实际操作与验收证据时，不能生成一个“已经恢复”的事实。

交付一张RPO时间线、一张RTO时间线，以及“最新备份能恢复”仍缺的三条证据。每条说明来源与验收方式，而不只写“加强监控”。
