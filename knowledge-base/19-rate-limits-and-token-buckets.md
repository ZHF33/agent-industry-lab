# 第十九讲｜每秒能处理两次，为什么还能突然接十次？限流与令牌桶

对应[API配额审查Agent](../examples/api-quota-review/README.md)。本课不发送请求、不改网关、不启动Redis，只做离线预算实验。

## 1. 先看两条不矛盾的规则

合成同步任务准备一次发送11个请求。配置写“每秒补充2个，桶最多10个”，值班同事认为：“等够六秒，总该能一次发11个。”这里混淆了补充速度与容器上限。

想象游乐场通行票：盒子最多存10张，每秒补2张；每次进入用1张。人少时存下的票可以支撑一阵突发，人多时票耗尽就需要等。但盒子再等也只有10张。

类比边界：真实限流器是状态和算法，不是真票；不同系统的准入、补充、时钟、并发与多层限制可能不同。今天限定连续补充、每请求消耗一个令牌的理想模型。

先答：每秒2次是否等于任何一秒都不可能接超过2次？在这个允许存票的模型中，不是。已有存量可以支撑突发；长期补充速度与短期突发容量是两种限制。

## 2. 限流、并发、排队、配额分别管什么？

**限流（rate limiting）**限制某个范围内单位时间的进入速度或请求准入。**并发**关注同一时刻有多少任务正在进行。**队列**暂存等待处理的任务。**配额**常用于一段较长时期的总量预算，但具体产品命名不同。

如果每秒进入2个请求、每个耗时10秒，持续稳定情况下可能堆起约20个并发任务；这个粗略例子假设系统稳定、持续到达，不是普适容量保证。限进入速度并不自动限制任务耗时或内存。

第15讲的队列可以承接等待，但队列也要有界和过载策略。今天的Agent仅审配置快照，不具备排队或实际限流能力。

小问题：限制同时运行1个模型请求，等价每秒最多1次吗？不等价。若一次耗时120秒，1个并发吞吐可能远低于每秒1次；若一次极快，1个并发也可能每秒完成多次。

## 3. 令牌桶里四个量

**令牌桶（token bucket）**可用四项描述：容量B、当前令牌b、每秒补充速率r、距离上次观察的时间Δt。令牌是算法预算单位，不是大模型文本Token，也不是API鉴权密钥。

按今天的理想假设，没有任何其他消费者，期间配置稳定：

```text
可用令牌 b_new = min(B, b + r × Δt)
```

`min`取两者较小值，防止超过容量。请求消耗d个令牌时，若b_new≥d才能按本例规则整体准入；成功后扣除d。真实限流器必须把判断与扣减作为受并发保护的操作。本课只计算投影，不执行扣减，不授权发送。

本例把批次定义为“全部一起准入的原子批次”。普通HTTP请求并不会自动共享这种批次语义；若逐个发送，会随到达时间和其他请求改变余额，必须另建调度模型。

## 4. 小数字一步算完

B=10，b=3，r=2/秒，Δt=2.5秒：

```text
新增 = 2 × 2.5 = 5
未封顶总量 = 3 + 5 = 8
可用投影 = min(10, 8) = 8
```

三个问题：批次8，在理想假设下足够；批次9，差1，至少再等1/2秒；批次11，大于容量10，再等也不能一次整体装下。

若将Δt改100秒：`min(10,3+200)=10`。不是203。**突发容量**限制存量，**补充速率**限制增长，两者互不替代。

再问：若速率0且当前只有3，需求4，需要等几秒？这个模型中没有有限等待能补足。不要做除以0，也不要输出“0秒”。

## 5. 理想等待不等于Retry-After

当d≤B、r>0且预算不足：

```text
理想等待 = (d - b_new) / r
```

这是静态推导，假设没有别人消费。如果共享API同时有其他任务，等半秒后令牌可能又被别人取走。模型计算不能保证下一次请求成功。

**Retry-After**是HTTP响应可能给出的重试相关提示，不能把这个离线公式输出擅自冒充服务器响应。是否重试还要看接口语义、幂等键、总截止时间和服务方要求。对于写操作，超时后是否已成功要核实；第11讲已解释“结果未知”，不是简单睡一会再发。

本例Agent不实际sleep，不改配额，不重发业务请求。它只建议人检查是否可拆批、是否有其他消费者、是否存在账户/方法/租户多层限制。

## 7. 分段读代码

以下是完整文件中的片段，不能独立运行：

```python
rate, elapsed = Fraction(rate), Fraction(elapsed)
available = min(Fraction(capacity), tokens + rate*elapsed)
```

**Fraction**是标准库的有理数，即分子/分母表示。输入“2.5”可精确表示5/2，避免先转二进制浮点再处理临界值。动作是把输入转为分数、乘时间、加存量、最后封顶。输出是理想可用量，不是服务器实时余额。

```python
if demand > capacity:
    return str(available), "oversized_batch", None
```

先检查单批容量上限，免得给不可能整体准入的需求算一个假等待时间。`str`把分数转成可打印文本。

```python
if rate == 0:
    return str(available), "no_refill", None
```

检查速率0后，才做除法计算等待。边界条件顺序很重要：如果余额已经足够，即便r=0，本次投影仍可满足，不必等待。

## 8. 生产里最容易出错的两个地方

第一是并发：两台机器都读到1个令牌，都判断足够，随后各自扣1，总共放过2次。单机字典或普通“先读后写”不足以做分布式限制。后续可评估Redis原子脚本、数据库事务或网关原生能力；不能说加上Redis就自动正确，还要看键范围、执行原子性与故障行为。

第二是时间：不同机器时钟偏差、快照陈旧、配置版本变化都会让推算失真。运行时限流器常需要合适时钟策略，本例用带时区快照和审核时刻只是审证据，不模拟网关实现。未来时间、范围错配、版本不一致时不应继续把投影当可信预算。

当前Agent内存锁的429仅表示API忙，与被审查的业务令牌桶不是一回事。这是真实实现边界，不能把两类429混成“已实现生产限流”。

## 9. 方案取舍

固定窗口计数容易理解，但窗口边界可能出现突发；滑动窗口更贴近连续区间但维护成本不同；令牌桶自然表达长期速率与短期突发，仍需准确状态。漏桶等机制还有其他平滑特征，今天只作方向，不把不同算法混写。

AWS API Gateway文档使用令牌桶解释速率与突发，且明确相关目标是尽力执行，不是保证绝对请求上限。这个官方例子也说明：不能把我们的数学上限直接当云平台的硬保证。[官方限流说明](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-request-throttling.html)

小项目可以先做只读容量审查；真要执行准入，优先用成熟网关或经并发验收的组件，明确范围、拒绝策略、观测和恢复。无检索需求时不必堆RAG/Dify/向量库。

## 10. 常见故障表

| 现象 | 优先核对 | 避免的误判 |
| --- | --- | --- |
| 等很久大批次仍过不了 | 单次需求是否超过B | 再加等待一定好 |
| 本地算够但仍429 | 共享消费者、多层限制、快照/配置 | 服务端一定错了 |
| r=0发生除零 | 是否先处理零补充 | 输出0秒重试 |
| 多机超发 | 判断扣减是否原子、键范围 | 每台算对总量就对 |
| 任务堆积 | 请求耗时、并发和队列上限 | 限流等于排队问题全解决 |
| 重试造成重复写 | 幂等与未知结果核对 | 429/超时一律立即重发 |

## 11. 练习与答案

1. B=5、b=1、r=2、Δt=3，可用多少？**5。**未封顶7，容量截到5。
2. 上题需求6，等几秒？**没有让6个一起准入的有限等待。**必须另评估拆分或配置，不是擅自调大B。
3. B=10、b_new=8、d=9、r=2，半秒后一定成功？**不一定。**该等待忽略其他消费，不保证真实准入。
4. 速率低能否仍瞬间很多请求？**可以。**桶中已有存量允许突发，长期与短期限制不同。
5. 看到Agent API返回429，能证明业务网关配额不足吗？**不能。**本例429来自单进程忙锁，得核具体来源。
