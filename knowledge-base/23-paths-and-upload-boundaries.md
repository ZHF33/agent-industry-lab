# 第二十三讲｜文件名不是存储地址：路径与附件接收边界

前置：第2讲数据契约、第7讲工具范围。关联[附件接收审查Agent](../examples/attachment-intake-review/README.md)。目标：能解释为什么资料里的路径不能直接变成程序打开的位置，并能区分文字检查、真实文件访问与内容安全。

## 1. 收到一张附件清单，为什么先不打开？

采购人员收到合成供应商清单：docs/spec.pdf、../outside.csv、data/table.csv。人的直觉是“都是文件名”。程序却可能把路径中的符号当动作：斜线区分目录，两个点可能指上级位置。如果直接把外部字符串接到存储根目录，结果可能超出原来约定的区域。

生活类比：仓库货架号只能在仓库内部定位；陌生人写“先出仓库再到隔壁”不等于获准到隔壁取货。类比边界：文件系统还有链接、平台规则与并发变化，不是只看一张地址纸能证明最终访问对象。

今天的MVP仅查清单文字，不保存附件、不解压、不打开磁盘路径。将“建议隔离”写在报告里，也不等于已经把真实文件移动进隔离区。

## 2. 路径的最小概念链

**目录**是组织文件的位置；**路径**是描述位置的形式。`docs/spec.pdf`由目录段docs和文件名spec.pdf组成。**相对路径**依赖一个起点；**绝对路径**直接给出所在系统的起始位置，例如某些系统的`/data/a.pdf`，或Windows的`C:/data/a.pdf`。

**路径分隔符**用来分段。Windows常见反斜线，很多接口使用正斜线；应用若先按一种规则检查、再按另一种规则打开，同一个字符串可能得到不同解释。驱动器相对形式`C:a.pdf`也不应被当作普通跨平台相对名。

`.`通常表示当前目录，`..`通常表示上级目录。本例协议直接拒绝这些原始分段，也拒绝空段，不先消除它们再当成正常文件名。**路径穿越**就是利用路径解释使访问越过允许范围的一类问题；并非所有含点的名字都有问题，`spec.v2.pdf`中的点是名字的一部分。

小问题：看到`.pdf`就一定是PDF吗？不是。扩展名是名字，真实内容可能不同；声明类型也只是声明。

## 3. 文字协议检查与文件系统检查是两层

Python的PurePosixPath/PureWindowsPath只计算路径表示，不访问操作系统。Path则还提供真实文件操作。本例故意采用Pure类，适合跨平台审查外部路径文字。

但Pure类不是安全打开器。即使词法检查合格，磁盘上的docs可能是一个**符号链接**，把访问指向别处。检查时与打开时之间，目录也可能被其他进程替换。这就是检查结果与实际使用对象之间的间隙，不能只靠字符串前缀比较消除。

生产接收通常应由服务端生成内部存储ID，将原始文件名仅作为展示元数据，并在受控权限和隔离存储下处理。若必须按目录访问，要按系统设计真实对象约束和安全打开方式；本课堂不提供一段“通用安全落盘”代码，也不声称resolve后就解决并发竞态。

反例：字符串`allowed-backup/x.pdf`以`allowed`开头，却不一定在`allowed/`目录里。字符串前缀不是目录成员关系，更不是最终文件对象的授权。

## 4. 为什么采用严格的小协议？

我们的合成清单约定：仅ASCII字母数字开头的分段，允许后续点、短横线、下划线；总长最多240，每段最多80；只用正斜线；拒绝绝对/驱动器形式、上级/当前/空段、百分号、冒号、特殊设备名、尾点。

这不表示中文文件名不安全。只是本MVP选择窄协议，避免声称已实现全部Unicode规范化和平台兼容。真实系统要支持中文时，应先定义编码、规范化、长度、存储映射与重复冲突处理，不能简单删除正则就宣布支持。

百分号为什么拒绝？`%2e`可能在某些层被解码成点。如果入口检查原始文本、下游再解码，语义可能变化。本例选择不接收编码路径，避免多层解释；不自动解码后重试，也不声称覆盖所有外部系统编码规则。

Windows特殊名字如CON不适合作普通跨平台文件段。我们也按不区分大小写的形式识别清单中的重复合法路径，这是保守协议选择；实际系统应按存储后端规则确定冲突口径。

## 5. 从输入到原因列表

下面为完整文件片段，不可独立运行：

```python
parts = value.split("/")
if any(part in {"", ".", ".."} for part in parts):
    return ["empty_or_dot_segment"]
```

输入是路径字符串；split将它按斜线拆成列表。`a//x.pdf`得到a、空段、x.pdf，所以拒绝；`a/../x.pdf`得到a、上级段、x.pdf，也拒绝。any表示只要一个分段符合条件就返回原因。

为什么不先用Pure路径的parts再查？有的路径库会折叠当前目录/空分隔，使原始异常写法消失。我们要检查的是本协议是否收到明确、唯一的形式，先保留原始分段含义。

```python
if size > POLICY["max_file_bytes"]:
    reasons.append("declared_size_exceeds_limit")
```

size是声明字节数，本例单文件合成上限5000000字节，严格大于才超限。5000000是十进制字节数，不把它含糊写成5MiB。程序校验整数而非布尔值；在Python中True可像1参与某些运算，因此用精确类型检查。

这仍不限制真实上传流量。外部可以少报大小，实际字节更多；生产服务需在传输/读取阶段限制实际数据量，不能只相信清单。

## 6. 声明类型与内容验证

本例只允许.pdf对应application/pdf、.csv对应text/csv。匹配仅说明两个声明相互一致；不说明文件可以安全解析，也不说明CSV不含对后续工具有害的内容。

内容嗅探、解析器安全、恶意软件扫描、隔离运行是不同环节，且都需要设计失败和不可用时的处理。扫描结果也不能无限期、无限版本复用；本MVP完全没读字节，所以固定写content_verified=false、malware_status=unknown。

手推样例：ATT-1路径正常、2048字节、声明PDF；无元数据异常。ATT-2是上级路径；ATT-3声明6000000字节且.csv对应的声明类型写成PDF，两个理由。异常附件数量为2，不是理由数量3；总声明字节2048+100+6000000=6002148。

## 8. 工程取舍与故障定位

| 情况 | 应核对的层 |
| --- | --- |
| 合法中文名被拒 | 本例窄协议限制，先设计Unicode支持 |
| 路径正常却访问别处 | 链接、真实对象权限、检查与使用竞态 |
| 清单小而上传很大 | 实际流量限制，而非声明值 |
| CSV声明一致仍有问题 | 内容与下游解析，不能靠扩展名证明安全 |
| Agent建议隔离但文件没动 | 本例没有文件动作，建议与执行分开 |

对象存储、杀毒服务、隔离队列和持久审计只有真实文件接入后才有意义；本例无需堆叠。模型负责取证与解释，程序负责严格白名单和数据契约。将清单交给RAG不会让路径变得可信。

## 9. 练习及答案

1. `spec.v2.pdf`含点是否违规？**本协议不违规。**不是独立的`.`/`..`段。
2. 元数据全通过可以导入吗？**不能。**还缺真实内容、权限、隔离与执行检查。
3. 只查`startswith(root)`够吗？**不够。**名字前缀不等于目录关系，真实对象也可能变化。
4. ATT-3两个问题算几个异常附件？**一个。**附件数与理由数分开，避免误报数量。
5. 本例已经执行恶意文件扫描吗？**没有。**只查声明，明确未知。
