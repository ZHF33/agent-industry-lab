# 第二十一讲｜昨天批准的操作，今天还能执行吗？审批有效期与单次消费

第3讲介绍暂停和恢复，第20讲介绍版本竞争；本课讲批准证据的生命周期。配套[批准时效审查Agent](../examples/approval-expiry-review/README.md)。不授予权限、不续期批准，不连接真实身份系统。

## 1. 一张签字单，为什么不能永久有效？

合成申请要给数据集A开只读权限。负责人上午批准，约定12:00:30前适用；申请随后可能改成数据集B，也可能被撤销。程序不能只看数据库某行写着approve就执行。

想象公司领料单：签字允许某人在某次申请中领指定数量，并不允许换货品、换数量、无限次领取。类比边界：真实权限依赖可信身份、业务政策和执行端，不是扫描一张签名图片即可验证。

小问题：审核者写了名字，是否已经证明是本人？没有。名字字段是声明，认证需要可信登录会话、身份服务等证据。

## 2. 批准至少绑定哪些对象？

**审批**是对明确提案作出的决策。一个可审计的批准记录通常需要关联申请ID、提案版本、动作、资源范围、审核者身份、决策、批准时间与有效期限，以及撤销/使用状态。

**范围**限定能做什么、对谁做，例如只读数据集A，不是所有数据集写权限。**版本绑定**防止申请改过以后沿用旧批准。**撤销**表示之后不再接受该批准。**消费**表示某次批准已经被对应执行流程使用，不应被重放。

消费规则应由业务决定：有些批准授权一次动作，有些是有时限的一组权限，不能一概要求所有权限都单次使用。今天限定一次访问授予提案的审查场景。

## 3. 用区间解释到期边界

本例规定有效区间为`[approved_at, expires_at)`：方括号表示包括起点，右圆括号表示不包括终点。

```text
approved_at <= 当前时刻 < expires_at
```

截至12:00:30，12:00:29尚在时间范围内，12:00:30已经不在。约定“到期时刻是否包含”必须写明，不能在不同服务各猜一种。

时间都要带时区。纽约时间与UTC文字不同但可代表同一瞬间；只比较字符串可能错，程序应解析为可比较时间。时钟偏差和请求排队仍需单独设计，不是多写一个时区就完全解决。

小问题：还没过期能否直接执行？不能，时间仅是其中一项。对象、修订、权限、撤销、消费都可能阻断。

## 4. 状态和时间不是一回事

一个最小状态方向可画成：待审核→拒绝，或待审核→已批准→已消费；已批准也可能撤销。过期可以由当前时刻计算出来，未必需要后台任务立刻把数据库字段改成expired。

这能解释常见现象：数据库仍显示approved，但执行门已因到期拒绝。若执行端只相信字符串状态，不核时间，它就可能接受旧批准。

不要把本次Agent图的人工review和被调查的批准记录混淆。review节点是让人接受“这份旧批准有问题”的建议；批准这份分析，不会把旧申请重新授权。

## 5. 纯离线实验：四种结果

前提：Python 3.11+，无额外依赖。在PowerShell进入仓库根目录：

```powershell
python --version
python knowledge-base/examples/approval_window_lab.py
```

完整文件：[approval_window_lab.py](examples/approval_window_lab.py)。脚本只返回原因，不改变任何业务状态。按源码推导的预期，未实际执行：

```text
before: ['snapshot_eligible_not_execution_authority']
boundary: ['expired']
changed: ['revision_changed']
replay: ['consumed']
```

第一项名字刻意长：快照条件满足，但还不是执行权限。第二项到期边界拒绝；第三项版本改变；第四项同一记录标记已经消费，不接受重复使用。

找不到python先检查解释器；找不到脚本先检查目录。返回expired是正确拒绝路径，不是需要绕过的环境故障。

## 6. 逐段看输入、动作、结果

以下是完整文件片段，不可独立运行：

```python
now, end = datetime.fromisoformat(as_of), datetime.fromisoformat(approval["expires_at"])
```

输入时间文本，动作是解析成时间对象。完整脚本检查两者有时区，避免拿“本地几点”混成同一瞬间。

```python
if now >= end:
    reasons.append("expired")
```

`>=`表示大于或等于，精确落实不包含到期终点。`append`把原因加到列表；多个条件可以同时失败，不必只给一个模糊的“审核失败”。

```python
return reasons or ["snapshot_eligible_not_execution_authority"]
```

有原因就返回全部原因；列表为空才返回快照可继续检查。这个例子省略真实身份、完整申请绑定、可信时钟和原子消费，不可当作完整权限验证器。Agent版增加对象/动作/范围、审核者合成名单和证据时效，但仍不是生产授权服务。

## 7. 为什么检查通过后还要原子消费？

假设两次重复回调同时到达，都读到consumed=false。如果分别检查后才写状态，两次可能都执行。需要真正执行端在授权规则下，把状态条件与消费动作原子处理，再配合业务动作的幂等和恢复方案。

这与第20讲CAS相关，但对象变成批准的生命周期。执行可能中途失败：先标消费再业务失败，如何恢复；先业务成功再标消费失败，如何防重复。事务、幂等键、状态机或outbox要按系统边界设计，不能随便用两行代码承诺“恰好一次”。

**重放**就是旧回调/旧批准再次被提交。防重放不能只检查姓名或时间；要绑定正确请求、版本、动作和消费状态，必要时校验签名与令牌范围。密钥和真实回调令牌绝不能放公开样例。

## 8. 平台的等待，不等于业务批准永久有效

LangGraph interrupt可暂停图，并凭thread_id定位检查点，Command恢复。它提供状态恢复机制；审核者身份、批准有效期和业务授权仍由应用负责。[LangGraph官方说明](https://docs.langchain.com/oss/python/langgraph/interrupts)

AWS Step Functions的回调模式可以等待外部任务结果，并提供超时相关机制。这里仅借它区分“请求已经提交”和“等待外部结果”；不把平台等待时限当作业务批准有效期，也不在本项目接AWS。[官方回调模式](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html#connect-wait-token)

心跳是“工作方仍有响应”的证据，不是“批准仍有效”；任务超时与用户撤销也不是同一事件。平台状态和业务状态需要明确映射。

## 9. 工程取舍与真实不足

短有效期可以收窄旧批准风险，但长任务可能在排队中到期，需要明确重审体验；过长则扩大状态变化窗口。没有适用于所有业务的固定分钟数。

实时查撤销状态更及时但增加依赖；缓存加快查询但可能延迟撤销生效；本例不缓存批准。真实执行优先保证身份/范围/原子状态，再考虑性能。当前内存检查点重启会丢，不具备持久审计、恢复或跨租户隔离。

本例精确ID查表无需RAG或向量库；LangGraph管分诊，n8n转发，Dify知识运营并非必要。不能因为有人工节点就把整个系统称为安全审批系统。

## 10. 常见故障

| 现象 | 优先核对 |
| --- | --- |
| 有approve仍被拒 | 时效、修订、范围、撤销/消费，而非只看状态 |
| 换资源后还能执行 | 批准是否绑定资源和动作 |
| 连点两次执行两遍 | 执行门原子消费与业务幂等 |
| 重启后找不到待审 | 检查点是否持久，不是旧批准自动失效 |
| 回调无效但任务还等 | 拒绝事件与等待状态是否被正确记录 |
| 报告过期却继续授予 | 执行器是否真的阻断，不只是模型提示 |

## 11. 练习与解释性答案

1. 截止12:00:30，在同一瞬间能用吗？**本课契约不能。**右端不包含，实际系统应明确约定。
2. 原来批A只读，改为B只读但版本没变，能用吗？**不能。**范围变更必须被发现，版本机制也需修正。
3. 人工接受“旧批准已到期”的报告，等于重新批准访问吗？**不等于。**本次review审的是分析建议。
4. 已消费但未过期可再执行吗？**本课一次性提案不能。**时间与消费状态两项都要满足。
