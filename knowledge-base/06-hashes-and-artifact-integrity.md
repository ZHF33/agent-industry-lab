# 第六讲：文件名字没变，内容真的没变吗？

配合发布包完整性复核Agent。先看文件指纹，再理解制品、批准清单与可信来源；

## 1. 从同名文件开始

同事给你config.txt，昨天也给了一个config.txt。名字一样，甚至大小一样，里面一个开关却变了。只比较文件名不够。人工逐字比较小文件可行，但上百个文件就容易漏。

可以给内容算一个固定长度的摘要：输入字节，经过哈希算法得到一串十六进制字符。**哈希**是这类计算方法，**摘要**是结果。SHA-256是本例使用的算法，显示为64个十六进制字符。生活类比是给内容算指纹，帮助检查它是否与手里那份基线一致。

类比边界：指纹比喻不能证明文件来自谁。攻击者如果同时替换文件和指纹，你照着新指纹比较也会“通过”。所以必须分别处理内容完整性和基线可信性。

小问题：名字相同、大小相同，内容一定相同吗？不一定。相同长度的字节可以有不同内容。

## 2. 先认识制品和清单

**制品**是准备交付或发布的文件，例如构建出的程序包、配置和说明。**清单**记录预期应该有的文件，以及每个文件的摘要。**基线**是用于比较的批准版本或记录。

项目中有两个合成集合：EXPECTED代表批准内容，ACTUAL代表提交内容。它们不是读取用户电脑的目录，只是源码里的短字节数据。

核对不能只看共同存在的文件。预期有而实际没有，叫missing；实际有但预期没有，叫unexpected；双方都有但摘要不同，叫mismatch；双方都有且摘要一致，叫match。空清单也不能自动视为可发布，因为没有任何批准内容可核对。

例如app.txt相同，config.txt改过，extra.txt多出来。工具保留三种结果，而不是只写一个“包有问题”。主管才能追问配置为什么改、额外文件是否应加入批准范围。

## 3. 代码逐步读：为什么传字节？

概念片段，不可独立运行：

```python
hashlib.sha256(value).hexdigest()
```

value是字节，不是文件名。sha256执行摘要计算；hexdigest把结果转换为十六进制文字，方便放入JSON。哈希函数不自动打开文件、不连接网络，也不替你判断内容的含义。

```python
b"synthetic build v1\n"
```

b前缀表示字节常量，末尾\n表示换行。改变换行也会改变字节。真实文件若Windows换行与其他系统不同，可能文本看起来相同但原始摘要不同。本项目明确按原始字节比较，不偷偷规范化。

如果业务希望比较规范化后的文本，必须定义编码、换行和规范化规则，并把这个规则作为另一种比较口径；不能把规范化摘要误称为原文件字节摘要。

小问题：把文件路径当成value算哈希能验证文件内容吗？不能，只会验证路径文字的字节。要比较内容，必须由受控读取层拿到内容。本案例不提供本机文件读取，避免模型任意访问路径。

## 4. 模型、工具和人工分别负责什么？

模型自主选择lookup_manifest、lookup_artifacts、verify_hashes。程序核对工具名与release_id，保证一次调查只查一个合成发布编号。工具执行真正的比较，再把结果返回模型。

模型整理“配置不一致、多出文件，应让主管核对”。它不能用提示词宣布哈希相同，更不能把“完整性相同”升级成“安全可上线”。计算结果作为integrity_report独立输出，不只藏在模型文字里。

人工审核要确认批准清单来自可信审批流程。项目假定EXPECTED可信，没有实现数字签名验证。**数字签名**是另一套用于核对签名来源及内容的机制，不是把哈希文件存进同一个压缩包就完成了。后续接实际制品仓库，再考虑可信基线来源和签名校验。

approve在此只记录接受调查建议，不部署、不签名、不删除制品。权限边界来自代码没有这些工具，而不只是模型被要求“请不要”。

## 5. 最小实验

前提：Python3.12+；只需标准库，无需模型、平台或文件数据库。在仓库根目录运行：

```powershell
python knowledge-base/examples/hash_lab.py
```

预期：same_content True、changed_content False、same_size True。示例比较两份相同字节、一份改过字节，再展示相同长度仍可能内容不同。本次只做静态语法审查，这里不提供虚构的运行结果。

逐行理解：先定义fingerprint函数；对输入字节调用SHA-256；把摘要返回；比较同内容摘要相等；比较改动摘要不同；最后比较字节长度。这个实验没有证明不存在所有理论哈希碰撞，也不是数字签名或恶意软件扫描实验。

## 6. 常见故障与工程选择

结果不同但肉眼一样：检查换行、编码、空格和末尾换行。摘要相同就认为来源可信：检查基线来源，完整性与身份真实性是不同问题。制品只有一个文件通过就放行：检查是否遍历预期和实际文件名的并集。空包被判通过：检查是否要求批准集合非空。

把全文件读进内存可能对大文件不合适；真实制品读取应分块处理并限制大小、位置和权限。但本例是很短的合成字节，标准库即可，不必先安装对象存储或缓存。需要跨团队审批和长期留存，再增加制品存储、持久检查点、审计与备份。

真实系统还要处理同名重复路径、压缩包路径穿越、文件替换与读取之间的竞态，以及读取版本的一致性。本例不解压、不读取实际路径，因此不能声称解决了这些问题。

计算摘要需要看到原始内容，但日志不需要保存原始内容；摘要也不等于脱敏。短、可猜测内容可能被离线枚举猜出，不能把真实身份证、电话等做简单哈希就当匿名数据公开。仓库只保留合成字节和工程摘要，不上传真实包或日志。

## 7. 课堂练习与解释性答案

一：文件和摘要都来自同一个陌生链接，摘要匹配就能信任吗？不能。它只能说明两者一致，可信来源需要另行验证。

二：额外文件没有出现在批准清单里，可以忽略吗？不能，可能是误打包或范围变化，应标unexpected并交审核。

三：哈希相同代表程序没有漏洞吗？不代表。哈希只比较内容，不理解业务行为，也不替代代码审查、安全测试。

四：有真实路径的读取工具是否应让模型随便传路径？不应，需要固定允许范围、访问身份、大小限制及读取版本控制。

五：主管approve后是否自动发布？不是。本例审核与部署分离，代码没有发布权限。
