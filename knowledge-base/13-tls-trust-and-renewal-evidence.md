# 第十三讲｜TLS证书：为什么“没过期”和“已续签”都不等于连接可信？

零基础，无需购买域名、申请证书或启动服务。关联[证书续期Agent](../examples/certificate-renewal-review/README.md)。

## 1. 先看值班场景

业务负责人问：“我们的网站周五证书到期，现在没问题了吧？”工单写着“新证书已签发”。如果只看这句话就结单，周五仍可能发生访问失败：证书可能没有部署到对外入口，某个节点还拿着旧证书，或者证书对应的是另一个名字。

生活类比是商店营业证：拿到新证件、把证件送到正确门店、顾客实际看到新证件，是三个动作。类比只说明证据链，证书并不认证商家诚信；TLS信任也不是行政审批。

今天学三个区别：**连接加密不等于对方身份已确认；日期合格不等于证书全部合格；签发成功不等于上线成功。** 学完能把一张工单拆成需要分别证明的事实。

## 2. TLS是什么，放在哪一层？

**TLS，传输层安全协议**，用于建立受保护的通信通道。HTTP是应用收发请求与响应的一种约定；常说的HTTPS，通常是HTTP通过TLS传输。它帮助防止传输中的窃听与篡改，并在常见网站访问中验证服务器身份。

```text
浏览器或Agent的业务请求
          ↓
HTTP：想请求哪个资源、收到了什么响应
          ↓
TLS：握手、身份验证、建立受保护通道
          ↓
底层网络连接
```

这里是概念分层，不限定所有HTTP版本都采用同一底层实现。先把“连接保护”和“业务回答正确”分开：加密可以保护一条错误的业务回复，它不能代替应用校验。

小问题：HTTPS返回200，能证明模型回答正确吗？**不能。** 通道、HTTP结果、业务内容分别验收。

## 3. 证书里有什么？私钥又是什么？

**数字证书**可以先看作一份有数字签名的声明：把某个身份信息与某个公钥关联起来，并包含有效期等字段。网站证书还涉及允许使用的名字等信息。**公钥**可以公开，**私钥**必须由持有者保护。

不要用“证书就是网站密码”记忆。客户端接收证书不意味着拿到了服务器私钥；服务器需要在协议中证明自己控制相应私钥。证书签名由谁签、客户端是否信任该签发链，也需要检查。

**CA，证书颁发机构**，负责在其政策下签发证书。客户端有信任的根证书集合；服务器提供的中间证书与叶子证书需要组成能验证的链。叶子证书是直接代表目标服务的证书；中间证书帮助连接到信任根。

这不是“名字写得像某CA就可信”。数字签名要由密码学运算核验，证书路径还要符合规则。证书文件里写了哪个域名，也不等于请求什么域名都能用。

## 4. 一次握手想确认哪些事情？

握手先理解成正式交流前的协商和证明。以常见TLS1.3服务器证书认证为例，双方协商协议参数和密钥材料，服务器提供证书链及相应证明，客户端进行验证，握手消息的完整性也要受到保护。随后用协商导出的密钥保护应用数据。

这段是机制概览，不要求第一课实现密码学。要知道“认证信息”与“实际加密数据用的会话密钥”有不同职责，不能把TLS简化成“所有网页正文都拿证书公钥直接加密”。更完整协议流程见[RFC8446](https://www.rfc-editor.org/info/rfc8446/)。

证书验证至少需要问：

| 问题 | 为什么不能省 |
| --- | --- |
| 当前时间是否位于有效期内？ | 昨天有效的证书今天可能过期，明天生效的证书今天还不能用 |
| 身份是否匹配要访问的名字？ | 给A服务的证书不能随便代表B服务 |
| 签名、链和信任根是否可验证？ | 自己写一份“我可信”的文件没有建立信任 |
| 用途、约束和算法是否符合验证规则？ | 不是所有证书都可用于相同角色与场景 |

吊销检查是进一步的验证问题，不要假定任何默认客户端都已做完整、实时的吊销检查。根集合、系统时间、客户端策略、OpenSSL版本和具体配置也会影响验证。

小问题：把验证关掉后连接成功，说明问题修好了吗？**没有。** 它可能绕过了身份验证，恰好掩盖了错误配置。课堂不提供关闭证书验证的修复方案。

## 5. 为什么续签要分成四层证据？

1. **签发证据**：新证书生成成功，归属哪个资产、编号是什么。
2. **部署证据**：配置指向新证书，是否应用到所有相关入口。
3. **观测证据**：从获准检查的位置、在明确时间，实际看到哪个证书。
4. **连接验证证据**：名称、链和策略等验证是否通过。

这些层次不能互相代替。资产清单里记录“新证书已部署”，也只是记录；如要宣称当前线上生效，需要合适的新观测。多入口、负载均衡或代理会让检查位置更加重要。

本仓库Agent只读取合成资产与续签记录，并计算时间；没有真正做TLS握手或证书链校验。因此工具明确返回current_endpoint_status=unknown。它能帮助值班人员整理问题，不替代线上验证工具。

## 6. 最小代码：看验证配置，再计算快照风险

配套文件[certificate_lab.py](examples/certificate_lab.py)。只使用Python标准库和本仓库Agent的时间工具，不访问网络、不加载私钥、不下载证书。

第一段建立默认客户端上下文：

```python
context = ssl.create_default_context()
print("require_peer_certificate:", context.verify_mode == ssl.CERT_REQUIRED)
print("check_hostname:", context.check_hostname)
```

**上下文**在这里是连接配置对象，和大模型的上下文不是同一技术概念。输入为默认配置；动作是创建并读取配置；结果只是两个布尔值。True表示配置要求，不代表已经验证任何网站。没有连接，就没有远端证据。

第二段复用Agent的assess函数，输入固定参考时间：

```python
report = assess(ASSETS["CERT-DEMO-01"], "2026-10-20T13:00:00+00:00")
```

它先把带UTC偏移的时间统一为UTC，再计算资产快照中的到期时间与参考时间之差。示例相差三天，即259200秒；本例策略把小于或等于72小时列为critical。**临界值是演示政策，不是TLS协议要求所有公司采用72小时。**

快照年龄另外计算：参考时间减观测时间。过旧、未来观测、有效期风险分别输出，不能把陈旧快照推成当前线上状态。

环境：Python3.12+，有ssl模块。Windows PowerShell先进入自己下载的仓库，再运行：

```powershell

python knowledge-base/examples/certificate_lab.py
```

```text

seconds_to_snapshot_expiry: 259200

```

## 7. 对照练习：只改一个条件

先预测，再由学习者选择是否运行：

- as_of改成`2026-10-20T09:00:00-04:00`。预期剩余秒数不变：它与13:00UTC是同一时刻。
- 改为`2026-10-23T13:00:00+00:00`。预期快照证书expired，同时快照stale_snapshot。不能据此断言线上仍部署着旧证书。
- 去掉UTC偏移。预期ValueError：Timezone required。程序拒绝替你猜时区。

解释：有效期判断依赖“哪一时刻”，不是日期字符串看着相同；资料新鲜度依赖“什么时候观察”。这是时间课的应用，今天新增的原理是这些时间证据为何无法代替TLS身份验证与部署验证。

## 8. 故障定位与取舍

`ModuleNotFoundError: agent`先确认完整目录存在，示例会按自身位置找Agent目录；不要为了消除错误随便安装同名第三方包。`No module named ssl`指向Python环境缺少SSL支持，需要修复解释器构建或安装，不代表网站证书坏了。

真实系统的CERTIFICATE_VERIFY_FAILED可能来自过期、名字不匹配、缺中间证书、根集合或时间等原因；不要只凭错误字符串断言唯一根因。握手失败与HTTP响应错误也不同：没有拿到HTTP响应，不应随便编造一个HTTP状态码。

选型上，已有证书平台通常应提供签发、部署和观测元数据，不需要为这个结构化核对上向量库。需要多节点实测时接入受控探测器或平台API，而非让模型自由访问用户提供的地址；工具先限制资产范围和权限，观测位置与时间进入证据。Agent仍负责解释与收集下一步，不自行续签上线。

## 9. 课堂验收与答案

**题一：新证书未过期，为什么客户仍报错？** 名字、链、配置、部署入口等尚需检查；“未过期”只回答一个条件。不能无证据选定根因。

**题二：工单为issued，能否改成线上已恢复？** 不能。缺部署、实际观测和连接验证。可以写“已签发，部署与线上状态待确认”。

**题三：示例两个True是否证明私有模型API连接可信？** 不能。只读到客户端配置，未对该API握手或验证。

**题四：三天前观测的旧证书到期了，当前服务一定不可用？** 不一定。可能已经换证；应取得有授权的新观测。旧证据仍要保留来源与时间。
