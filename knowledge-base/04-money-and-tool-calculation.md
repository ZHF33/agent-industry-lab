# 第四讲：报价明明便宜，为什么总价反而更贵？

配合供应商报价复核Agent，先理解金额、比较口径和计算工具，再理解为什么模型不能靠口头判断价格。

## 1. 从买100件商品开始

甲每件10.20元，运费20元；乙每件9.90元，运费80元。只看单价会选乙。但算一遍：甲为10.20×100+20=1040元，乙为9.90×100+80=1070元，甲总价更低。

这不是复杂算法问题，而是比较口径问题。**口径**就是“大家按同一组条件来算”。比较100件与100箱、人民币与美元、含税与不含税，不是在比较同一种价格。本例统一100件、CNY（人民币的币种代码）、货价加运费、税前。其他费用没有被自动假设为零，真实采购必须另行核实。

生活类比：两家外卖菜单价不能替代结算页。类比边界：采购还涉及交期、质量、合同、税费与供应商资格，单个总价并不能决定最终采购。

小问题：乙单价更低，所以一定更划算吗？答案：不一定，先统一数量、单位、币种和费用范围，再检查交期等条件。

## 2. 谁负责算，谁负责解释？

模型适合阅读工具结果、解释差异、列出待核实问题。金额运算由确定的代码完成。**确定的计算**意味着相同输入按同一规则得到相同结果，便于核对。

项目中有三个只读工具：lookup_request取采购需求，lookup_quotes取报价，compare_costs计算总价。工具不更新订单或库存。模型自主选择工具，程序检查工具名和询价编号，执行后把真实结果返回模型。图要求三个工具都经过后，才接受最终建议。

这也不是“用了计算工具就不会错”：如果录入的单价、单位或费用本身错，计算会准确地算出错误输入的结果。人的审核仍要看报价原件，来源编号只说明用了哪条资料。

## 3. 金额为什么写成字符串？

编程中的float是一种二进制小数表示法。有些十进制小数不能被它精确表示，就像十进制写1/3需要无限多个3。因此金额输入采用字符串，例如 `"10.20"`，交给Python标准库的Decimal处理。

```python
from decimal import Decimal
unit_price = Decimal("10.20")
```

输入是文字“10.20”，动作是按十进制解释，结果是Decimal金额。不要先用float再传给Decimal，例如Decimal(0.1)，因为前一步已经引入了二进制近似。也不要为了看起来正确，最后再随意截掉几位小数。

这只是最小示意，不能当作完整项目运行；完整示例是配套knowledge-base/examples/money_lab.py，项目实现见examples/supplier-quote-review/agent.py。

小问题：字符串金额就能直接相加吗？答案：不能。普通字符串相加是在拼接文字，必须先转换为Decimal并校验。

## 4. 代码一步一步：校验、运算、舍入

项目money函数先要求输入为长度有限的字符串，转换Decimal后检查：不是NaN（非数字），不是Infinity（无限值），不能为负，也不能超过演示范围上限。

边界不是为难输入者。缺运费和运费0元意义不同：前者不知道，后者是明确免费。函数不能把None（缺值）自动改成0。费用缺失的报价保留问题并让人工补资料。

```python
total = unit_price * quantity + freight
```

输入是十进制单价、整数件数、十进制运费。动作是按采购数量算货价再加运费。结果仍是Decimal，不让模型重新心算。

```python
total = total.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
```

quantize在这里表示“按0.01的精度整理结果”，即保留到分。ROUND_HALF_UP是本例选择的舍入规则，正金额遇到半分向上。这不等于所有财务业务都应选它；合同、币种最小单位和会计规则需要另行确定。项目只在总金额最后一步舍入，不能默认为先舍入单价与最后舍入总额等价。

输出用字符串，例如"1040.00"，避免JSON输出阶段又转回float。某些调用者需要数值比较时，也应按十进制解析，不能按文字排序金额。

## 5. 四家报价，哪些可算，哪些要停？

| 报价 | 可计算总价 | 要人工看什么 |
| --- | --- | --- |
| A：10.20元/件、20元运费、5天 | 1040.00 CNY | 报价真实且有效、采购条件一致 |
| B：9.90元/件、80元运费、9天 | 1070.00 CNY | 需求7天，交期超出 |
| C：9元/件，运费缺失 | 不生成完整总价 | 补运费，不能当0 |
| D：1.50 USD/件、2 USD运费 | 不参加CNY直接对比 | 汇率时点、费用口径等需另定 |

代码仍保留C/D的记录，不偷偷删除不方便比较的数据。缺数据不是低价，也不是高价，而是当前不能按统一口径比较。B可计算但交期不满足，价格计算和交付可行性是两个维度。

## 7. 常见错误与工程取舍

金额出现奇怪尾数：检查是不是用了float或先Decimal(float)。没有运费却得到完整总价：检查默认值是否把缺失变为0。美元报价“更便宜”：检查币种过滤。服务返回的金额字符串排列不正确：检查是否按文字排序，"100"按字符排序可能在"20"前。

单价和总价差一分钱：写清在哪一步舍入，再按合同规则检查。Decimal不是无限精度魔法，计算受上下文精度约束。本例限制金额和数量，默认精度足够覆盖演示乘加；更大数据或复杂比例分摊需要明确精度和误差策略。

这类工具用标准库即可，不必为了四条结构化报价安装向量数据库。后续若接PDF抽取，才增加文档处理、抽取质量校验及来源定位。若模型可调整参数，则工具契约还应限制数量、币种和询价范围，不能允许跨采购单取资料。要真正下单时，另建审批、幂等与授权流程。

## 8. 课堂练习和解释性答案

练习一：丙只写“运费另议”，可以按0来比较吗？不能。0是明确金额，另议是未知条件。输出应保留缺项。

练习二：不同币种能不能直接比数字大小？不能。需要约定汇率来源、时点及换汇成本，当前案例不实现换汇。

练习三：模型说A最好，程序是否应直接下单？不能。只核对了有限价格和交期，质量、供应商资格、合同还需人工判断。

练习四：所有数都保留两位小数是否足够？不一定。单价可能需要更多位，货币也不都使用两位最小单位；舍入规则必须与业务契约一致。
