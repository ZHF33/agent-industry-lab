# 第41讲 已知失败与缺证状态

一张报销单有三份必需材料，其中一份已被财务确认有误，一份还没交。若界面只显示“未通过”，同事可能只改第一份，下一次又被要求补第二份。工程系统可以把明确失败和缺证同时保存，并给一条总状态。报销类比只解释资料状态，具体维修结案条件由企业规程定义，本课使用合成清单。

## 三种观测与一个总判定

每个必需项有三种状态。通过表示有来源的肯定记录，失败表示有来源的否定记录，缺证表示尚无该项观测。程序可用字典表示已收到的项目，用真假布尔值表示结果，键不存在就表示缺证。布尔值只含 True 和 False 两种，未知靠字段是否存在单独表达。

记 F 为失败项集合，M 为缺证项集合。规则按以下顺序判断，F 非空时为 blocked，意为已有阻塞；F 空而 M 非空时为 needs_evidence，意为需要补证；F 和 M 都空且必需清单已确认非空时为 ready_for_review，意为可以提交人审。所有分支均返回完整的 F 和 M，所以总状态可以概括准备度，列表仍能支持一次补齐。

| 维修记录 | 试运行记录 | 余料退回 | 总状态 |
| --- | --- | --- | --- |
| 通过 | 失败 | 缺证 | blocked |
| 通过 | 通过 | 缺证 | needs_evidence |
| 通过 | 通过 | 通过 | ready_for_review |

**小问题**　发现失败后马上停止检查剩余项目，会丢什么？

**解释**　可能漏掉尚未遍历的缺证项。合成规则选择先汇总全部项目，再判定总状态。生产查询如果代价高，可考虑分阶段查询，但报告必须说明检查范围。

## 为什么空清单值得单独判断

Python 的 all 检查输入里是否每一项都为真，空输入的结果是 True。这一数学约定便于组合逻辑，但不能据此认定“没读到必需项清单”就通过了结案核查。先确认清单加载正确，再逐项找对应观测。也不能对“已经收到的几项”调用 all，就认定全部必需项目已完成。

**小问题**　只收到一条通过记录时，all([True]) 为真，是否能得到准备完成？

**解释**　还要枚举其余必需项。本课总状态按规定清单计算，已收到的一条不能决定其他项。若业务明确规定允许空清单，应另定义该场景和依据。

## 静态可复查的实验

准备 Python 3.11 或更新版本，从仓库根目录运行 [课堂脚本](examples/evidence_verdict_lab.py)。

```powershell
python knowledge-base/examples/evidence_verdict_lab.py
```

函数接收必需项名字列表和布尔观测字典。先拒绝空必需项，再分别建立失败和缺证列表，最后计算状态。课堂假定观测均为布尔值且项目名在范围内。完整工程会检查值类型和来源编号。预期输出如下，代码只做静态检查与手推。

```text
blocked failed=['trial'] missing=['return']
needs_evidence failed=[] missing=['return']
ready_for_review failed=[] missing=[]
all_empty True
```

若返回值的 missing 为空但明知缺了项目，检查是不是遍历了 observed 而未遍历 required。若把字符串 "false" 直接放进布尔判断，它会被当作非空文本，类型校验应在进入判定前处理。

## 工程位置和练习

[维修工单结案证据复核 Agent](../examples/maintenance-closure-review/README.md) 使用这个结构保留失败、缺证、来源和人审记录。当前合成记录的 passed 字段由样例提供。真实应用需读取原始文件、签字权限、规程版本和撤回记录后才能形成可信观测。这里的判定法是必需项聚合契约，也可用于其他资料复核。加入不适用项时，应保存其授权依据，才能从本次必需集合里排除。

练习：把第三行的 return 改为 False，其他项不变。答案是 blocked，失败列表只有 return，缺证列表为空。再删掉 return 键，状态变为 needs_evidence。两种变化对应不同补救动作，一种需改正，一种需提供资料。
