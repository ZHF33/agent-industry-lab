# 第二讲：表格填对了，为什么还不能说明内容是真的？

面向零基础读者。本篇为正式讲义。前置知识只需要理解第一讲的“请求”：一方向另一方发出“请帮我处理”的消息。不需要先会写 Python。

学习目标：能看懂一份结构化输入；分清格式正确、业务合理和事实真实；解释缺字段、额外字段、自动转换和字段别名；知道如何把错误挡在模型调用之前。

## 1. 从填报名表开始

报名表要求“姓名、人数、联系电话”。有人只填姓名，有人把人数写成“很多”，有人把电话号码填到人数栏。工作人员先检查表格，才进入后续安排。

软件也需要这样的检查。我们把双方关于字段、类型和限制的约定叫数据契约。这里不是法律合同，而是“怎样提交，怎样回应”的技术约定。

但电话号码格式正确，不证明号码属于填写者。把姓名填完整，不证明他是登记的旅客。因此要分三层：结构检查、业务规则、事实核验。

| 层级 | 问什么 | 本项目示例 |
| --- | --- | --- |
| 结构 | 字段和格式合不合要求 | job_id 合法吗，copy 是不是非空文本 |
| 业务 | 在这个流程里允不允许 | 有阻塞问题能不能批准 |
| 事实 | 内容是否被可靠证据支持 | 商品原料是否真是这些 |

停一下：模型输出了一份格式完美的 JSON，就能自动批准吗？不能。结构检查只完成第一层。

## 2. 看懂 JSON，不先背术语

JSON 是一种表示数据的文本格式。大括号包住一组字段；冒号左边是名字，右边是值；方括号表示一组项目。

```json
{"job_id":"contract-demo","copy":"Demo Bread","max_chars":100}
```

job_id 是任务编号，copy 是文案，max_chars 是字数上限。双引号里的 100 是文本，没引号的 100 是数字。这份片段只介绍三个字段，不能单独作为本项目完整请求：完整请求还需要 product 和 claims。

所谓类型，就是“这一格应该放哪一种值”。str 表示文本，int 表示整数。字段缺失、空文本、null 并非同一种情况：缺失是没交这一格，空文本是交了但没有文字，null 是明确交了一个空值。是否允许，需要逐字段规定。

## 3. 门口检查与 Pydantic

Pydantic 是项目使用的 Python 数据解析与校验库。可把模型定义理解为可执行的表格要求。它不是聊天模型，这里的 model 指数据结构定义。

仓库 ReviewInput 规定了：编号的字符和长度、商品对象、声明数组、文案文本和字符上限。Field 用来给某个字段增加限制。例如 max_chars 的 ge=1、le=20000 表示从 1 到 20000。

这些限制属于当前应用契约，不是所有网站都必须采用的通用标准。

输入不符合结构要求时，程序产生 ValidationError，也就是校验错误。FastAPI 接口会把对应请求输入错误表达成错误响应；直接在 Python 里解析时，则表现为异常。两种入口不同，不要把“Python 抛异常”直接当成已经发出了 HTTP 请求。

## 4. 两个容易漏掉的细节

外部文案字段叫 copy，程序内部叫 content。alias 就是别名，它负责把外面的名字对应到里面。向外输出时是否使用别名，需要明确设置；不能以为输入用了 copy，所有输出就自然都叫 copy。

第二个细节是转换。默认情况下，某些输入可以被转换，例如数字文本可能变成整数。严格模式则会拒绝这一例。默认解析并不等于不检查，严格模式也不等于事实可信。

为什么需要选择？人工表单可能方便接受数字文本；模型工具参数或金额字段可能要求更严格。不能为所有字段机械使用同一种策略。

## 5. 实验准备与运行

前提：仓库的 .venv 环境已安装 requirements.lock。PowerShell 是输入命令的窗口，当前目录是命令正在使用的文件夹。

```powershell
Set-Location 'H:\CodeX\Carreer\agent-industry-lab'
.\.venv\Scripts\python.exe knowledge-base\examples\input_contract_lab.py
```

第一行进入项目文件夹，第二行用项目自己的 Python 执行实验。在其他电脑上修改仓库路径。

实验直接读取项目现有 ReviewInput，不调用模型、n8n、Dify 或真实业务服务。

| 操作 | 预期结果 | 学到什么 |
| --- | --- | --- |
| 提交完整合成请求 | 解析成功 | 符合结构可以进入后续规则 |
| 读取内部 content | 得到外部 copy 的值 | 别名映射输入 |
| 分别按默认和别名输出 | 字段名字不同 | 输出契约要明确 |
| 用非法编号、0 上限、空文案 | 都被拒绝 | 检查具体字段与限制 |
| 将 100 改成文本 | 默认转换，严格模式拒绝 | 类型策略可以不同 |
| 加入未知字段 | 当前模型忽略该字段 | 多填了字段不一定报错 |
| 调用已有审核规则 | semantic_verified 仍为 false | 解析成功不等于事实可信 |

PASS 表示对应检查符合预期；Traceback 表示程序报错。必须检查程序完整结束，不能只看第一行成功。

## 6. 为什么未知字段值得警惕？

当前模型会忽略没有定义的字段。用户把 max_chars 拼错，同时接口给该字段提供默认值时，可能导致用户以为设置成功，服务却用了默认值。本项目 max_chars 是必填，所以只拼错时会因缺字段失败；如果正确字段也存在，额外字段则可能被忽略。

对用户输入究竟忽略还是拒绝额外字段，需要设计。拒绝能更快暴露拼写错误，但也可能影响兼容；允许并保留又增加误用风险。教程说明当前行为，不偷偷宣称项目已经采用最严格策略。

## 7. 接入 Agent 时，检查放在哪里？

输入 → 结构检查 → 业务规则 → 必要模型/工具调用 → 输出检查 → 人工审核。

检查应尽早发生，错误材料不必先花模型费用。模型返回结果也要检查；用户输入检查通过，不代表模型输出就天然符合要求。

JSON Schema 是可描述字段要求的一种规范。模型接口可以用它描述预期结构，数据校验库也能生成相关结构描述。但只把 Schema 交给模型不代表完成本地验证，更不代表内容正确。检索引用、业务校验和人工判断仍各有职责。

不需要为这个小实验安装队列、向量数据库或工作流平台。等遇到相应问题再引入组件。本篇没有完成真实 RAG 或工具模型验证。

## 8. 课堂练习

一、给一段看起来正确的 JSON，能否证明它满足接口要求？不能，还要检查字段、类型和限制。

二、严格模式通过了，是否证明商品描述是真的？不能，它仍是结构层判断。

三、字段别名只是“换名字”，为什么需要测试？因为输入解析和输出序列化可能采用不同名字；调用方可能收不到自己期待的字段。

四、忽略未知字段一定是错误吗？不是，但必须是明确设计，并考虑拼写错误和兼容代价。
