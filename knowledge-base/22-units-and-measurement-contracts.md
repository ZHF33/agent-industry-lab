# 第二十二讲｜50到底热不热？单位、温差与测量契约

前置：第2讲字段契约、第5讲时间、第8讲数据质量。学完能说明：为什么一个数字不是完整测量，为什么温度换算有平移项，以及为什么采样点不能直接变成持续时长。配套[冷链温度异常Agent](../examples/cold-chain-excursion-review/README.md)。

## 1. 两个设备都写50，能直接比较吗？

收货员收到一条温度50的记录。一台设备输出摄氏，另一台输出华氏。如果先比较数字再看单位，系统可能把不同物理状态当成同一状态。我们只讨论虚构工业材料和合成流程阈值，不推导真实食品、药品或材料放行标准。

生活类比是“两袋各重10”：10克与10千克差很多。类比边界：温度不像质量那样只乘比例；不同温标的零点也不同。把所有换算都写成乘法，会产生新的错误。

**测量契约**是约定怎样理解一条读数：数值、单位、对象、采样时刻、设备/来源、质量标记及适用范围。**元数据**就是解释数据的数据，例如unit不是温度本身，却决定value如何解释。

小问题：JSON语法正确，温度就可信吗？不。语法只是能读，字段类型正确只是能按约定处理；单位可能错标、设备可能失准、记录可能属于另一运单。

## 2. 从物理状态到数字，再到比较

处理链是：设备对物理状态取样→记录数值及单位→校验对象与时间→转换到统一表示→使用同一单位的阈值比较→附来源解释结果。

转换不应该覆盖原始记录。原始50°F、规范化10°C以及换算规则应能对应，方便审计。如果后来发现设备配置把摄氏错标华氏，保留原值才能调查；公式再正确也修不好错标。

本例工具只接受字符串形式的小数和明确C/F，不猜unknown，不把空值当0。**规范化**指不同合法表示转换到统一形式，不是把不合法输入悄悄改成看起来合法。

## 3. 为什么华氏转摄氏既减又乘？

用两对温标参考值建立直觉：0°C对应32°F；100°C对应212°F。因此摄氏相差100格，华氏相差180格，每华氏1格对应摄氏100/180=5/9格。摄氏零点在华氏32，不在华氏0。

设F是华氏读数、C是摄氏读数，先从F中减去32，去掉零点差，再乘5/9调整每格大小：

```text
C = (F - 32) × 5/9
```

50°F的手算：50−32=18，18×5/9=10，所以是10°C。不能只写50×5/9；那会得到约27.78°C，因为忘了零点。摄氏转华氏反过来：F=C×9/5+32。

**仿射变换**是“先按比例缩放，再平移”的一类关系，先理解动作再记术语。这里换算公式来自温标关系，不是模型从文本猜一个数。NIST提供[精确换算表](https://www.nist.gov/pml/owm/si-units-temperature)；参考表中的近似常见温度值不要与精确公式混为一谈。

小问题：32°F是否比0°C热32度？不是，二者表示同一温度状态。

## 4. 温度值与温差，为什么不能共用一个公式？

如果从50°F升到68°F，华氏温差是18°F。两端换算成摄氏分别10°C、20°C，温差10°C。

```text
ΔC = [(F₂−32)−(F₁−32)] × 5/9
   = (F₂−F₁) × 5/9
   = ΔF × 5/9
```

Δ表示“变化量”，下标1/2表示前后两个读数。减法中32被抵消，所以温差换算没有平移项。18°F的温差是10°C的温差；18°F的绝对读数却是−70/9°C，约−7.78°C。

因此字段最好区分temperature与temperature_difference，文档也说清单位语义。写“下降18°F”却拿绝对温度函数处理，会得到完全错误的变化量。开尔文与摄氏的绝对值也有零点差，而温差大小一致；本例代码不支持K，遇到K应拒绝，而不是擅自继承正文提到的知识。

练习：温差9°F换成摄氏温差多少？5°C，计算9×5/9；没有减32。

## 5. 阈值、相等边界与数值表示

合成流程允许2°C至8°C，约定上下端都包含：2≤C≤8。本例用严格小于2或严格大于8定义异常点。等于8不异常；但这只符合本例约定，真实产品需读取正式政策与版本，不能复制此范围。

数字还可能受到计算表示影响。**浮点数**用有限二进制位近似表示许多数值；许多十进制小数不能精确表示。代码采用标准库Fraction，即分子/分母表示的有理数，把小数文本转为精确分数。本例50°F精确得到10，18°F绝对读数保留−70/9，不先四舍五入再判断。

这并不使传感器无限精确。设备的分辨率、校准偏差、测量不确定度与程序算术误差是不同层。软件算术精确，不代表靠近8°C的一条读数足以做真实质量放行。本MVP没有测量不确定度模型，也没有校准证书接入。

## 7. 逐段读输入、动作、结果

以下片段来自Agent，不能独立运行：

```python
number = Fraction(value)
if unit == "F": number = (number - 32) * Fraction(5, 9)
elif unit != "C": raise ValueError("Supported units: C, F")
```

输入value是已通过小数文本校验的字符串；动作是建立有理数并按单位选择换算；结果统一为摄氏。`if/elif`只选符合条件的分支。不能把未知unit当作C的默认分支，否则单位丢失不会被发现。

```python
if number < Fraction(-27315, 100):
    raise ValueError("Below absolute zero")
```

这是物理下界检查，不是产品质量检查。类型校验、物理合理性、设备可信度、业务阈值分别有职责，不能有一层就省略其他层。

例子里的Fraction(18)×Fraction(5,9)专门表示温差；celsius("18","F")专门表示绝对温度。函数名与字段语义应配合，不应只凭两个参数都是数字就交换用途。

## 8. 采样点为何不等于暴露时长？

12:05读到10°C、12:10读到10°C，只证明两个时刻的读数。中间可能变化。若采用“左端保持”估计，就是假设12:05读数代表随后到12:10的5分钟，得到300秒估算；这不是300秒真实连续观测。

本例只允许间隔不超过300秒时做这种明确标注的估算。12:10到12:20间隔600秒，全部记未知，不按最后一条高温补成超温600秒。缺口前后有相同读数，也不能证明中间没变化。

窗口1200秒，样例分为：区间内估算300秒、超上限估算300秒、未知600秒，总和1200。这个守恒式能检查代码是否漏算或重复计时，不能证明保持假设正确。

## 9. 工程取舍与失败排查

| 方案/问题 | 判断 |
| --- | --- |
| 全存原值、每次临时转换 | 灵活，但不同模块可能用错公式；集中转换函数并保留原值 |
| 入库仅保留规范化值 | 查询方便，丢原值会妨碍审计；保留单位与换算版本 |
| Fraction与浮点 | 前者适合本例小量精确演示；大规模遥测要按性能、精度和存储设计 |
| 50突然触发异常 | 先核单位、对象、时间、量程与设备配置，别直接提高阈值 |
| 全部读数合法却报告未知 | 类型合法不等于时间覆盖完整，检查采样间隔与窗口边缘 |
| 模型说可以放行 | 模型建议不具放行权限，执行端不能将自然语言当批准 |

当前项目只精确查表，没有海量遥测数据库、校准系统、对象文件、RAG或真实物流适配；LangGraph负责分析循环，n8n负责转发。基建应由数据规模、延迟与可靠性要求驱动，不能为一个换算公式引入向量库。

## 10. 练习及解释性答案

1. 50°F与10°C哪个高？**相同。**换算后相等；只比较50与10是错误操作。
2. 从50°F升到68°F是多少摄氏变化？**10°C。**温差18×5/9。
3. 8°C是否异常？**本例不异常。**上下端包含，真实政策另核。
4. 未知单位可让模型猜吗？**不能作为可信转换。**可请人核设备配置，不能据猜测做确定判断。
5. Fraction算得精确就可发布质量证书吗？**不能。**设备校准、不确定度、产品规则、身份和权限仍缺。
6. 两个高温点相隔10分钟，能写连续超温10分钟吗？**不能。**本例长间隔记未知，估算也必须说明假设。
