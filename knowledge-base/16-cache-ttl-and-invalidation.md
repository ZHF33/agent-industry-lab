# 第十六讲｜缓存与TTL：为什么“还没过期”不等于“价格是新的”？

零基础，不安装Redis，不清缓存，不改商品。配套[商品缓存一致性Agent](../examples/product-cache-review/README.md)。

## 1. 三分钟有效期里的旧价格

合成商品权威库11:00从8.50改成9.00元，页面仍显示8.50。值班人员查缓存，TTL还有180秒，于是认为“缓存没过期，应当没问题”。这里把“键还允许存在多久”当成“内容符合当前业务事实”。

类比前台抄了一张价目表，约定十分钟后换新；第三分钟老板已经改价。纸还没到约定丢弃时间，内容也可能过时。类比边界：真正缓存还涉及多进程、网络和并发，换纸不能解释全部一致性问题。

今天学会把三个问题分开：数据存在哪里、这份副本何时失效、它来自权威资料的哪个版本。交付一个改价与读缓存的时序图。

## 2. 缓存到底缓存了什么？

**缓存（cache）**是保存可重复利用结果或数据副本的一种机制，常用来减少重复计算和访问开销。**权威来源（source of truth）**是业务约定由谁负责该事实，不表示它天然永远正确。

例如商品库负责价格，缓存保存查询结果。应用可以先查缓存，命中就返回，未命中再查商品库并写入缓存。这种常见思路称为**旁路缓存或cache-aside**，今天是概念说明，不是Redis独有功能。

```text
查询商品 → 缓存命中？ ─是→ 返回副本
                  └否→ 查权威来源 → 写缓存 → 返回
```

**命中**表示找到了可用缓存项，不证明内容最新；**未命中**不一定是故障，可能首次查询、过期、被淘汰或被主动删除。命中率高也不能独立证明业务质量好。

小问题：系统100%命中旧价格，是否是一个成功的优化？**不能只按命中率判断。** 更快返回错误事实会造成业务问题。

## 3. TTL到底测哪件事？

**TTL，Time To Live，剩余生存时间**，用于描述缓存键的到期时间约束。以Redis TTL命令语义为例，正数表示剩余秒数，-1表示键存在但没有过期设置，-2表示键不存在。不能把所有负值都显示成“已过期”。

| 观测 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| TTL=180 | 该次查询返回了约180秒的剩余过期时间 | 来源版本最新、期间绝不删除、价格正确 |
| TTL=-1 | 那次查询时没有设置过期 | 永久可靠、不会被淘汰或主动删除 |
| TTL=-2 | 那次查询未找到键 | 一定是自然到期，或业务资料不存在 |

TTL观测是一个时点的数据。后来有人刷新、删键、重写或系统发生变化，原数字就不等于现在的状态。把观测180秒减去经过时间，只能形成不发生其他变化的投影，不能当作实时查询。

零秒也需谨慎理解：秒级剩余时间观测在临界位置，不能依据旧快照断言实际键当前一定在或一定不在。本例把它标为elapsed_ttl_projection，实时presence保持unknown。

## 4. 生命周期、资料年龄、来源版本三条线

缓存写入时刻、源资料更新时间和观测时刻分别有不同用途：

```text
10:58 缓存写入源版本v1，价格8.50
11:00 权威商品变成v2，价格9.00
11:05 观察缓存仍v1，TTL剩180秒
```

缓存到期倒计时没有自动跟随商品改价。即使我们刚刚读取它，这份副本也可能源自旧版本。“刚查到的旧资料”与“刚更新的资料”不是一回事。

版本可以是修订号、事件序号或其他业务标识，但必须有定义。字符串v10与v2不能随便按字典序判断新旧；本例仅检查是否相等。版本相等也可能是标记错误，所以字段内容和生成过程仍要核对。

前面的新鲜度课讲观测年龄，本课新增的重点是：副本即使尚未到期且观测很新，也可能因为权威来源更新而失去业务有效性。

## 5. 更新后怎样避免一直读旧副本？

一种思路是**主动失效**：权威资料更新后，让对应缓存失效，下次读取回源。另一种是刷新缓存数据；还可以用版本化键，让新版本数据用不同键读取。它们各有成本与失败路径，不是选一个名字就自动一致。

特别看并发回填的反例：

1. 请求A未命中，开始读取旧版本v1。
2. 管理员更新源为v2，并删除缓存。
3. 请求A稍后把之前读到的v1写回缓存。

删除执行过了，旧资料仍可能重新出现。**竞态**指多个操作的相对顺序影响结果。处理办法要结合系统，例如版本检查、写入条件或有序失效机制；不能给“更新后删一下缓存”就宣布一致性已解决。

这里不提供可操作生产的修复脚本。要先明确写入来源、并发顺序、失败重试和业务允许的陈旧窗口，再选具体机制。

## 6. 为什么TTL短一点也不是万能方案？

缩短TTL可能减少某些陈旧窗口，却增加回源负担。大量键同一时刻过期，许多请求同时回源，可能压垮原系统，这类同时失效集中访问的问题常被称为**缓存雪崩**的一种情形。

单个热门键过期时，很多请求同时重建同一结果，也可能造成集中负载。不同场景可考虑错开到期、单飞重建、限制并发或在明确政策下暂时使用旧值等策略。**单飞**先理解为让一组相同请求由一个重建动作负责，其他请求等待或使用约定的替代路径。

这些策略都要评估业务：商品收费、权限判断和普通内容摘要，对旧值的容忍度不同。不能为提高可用性就默默用旧权限或旧结算价。今天只建立取舍地图，后续才写并发控制代码。

## 7. 多层缓存为什么需要逐层找证据？

真实页面可能经过应用内存、Redis、网关、CDN、浏览器等多层。删了Redis并不保证浏览器展示立即变化；请求也可能根本没经过你检查的那一层。

**CDN**可以先理解为靠近用户分发内容的一类服务；这里不要求购买或配置它。需要核对请求路径、缓存键、版本和响应头等证据，而不是根据“页面还旧”盲目反复删同一个键。

同样，大模型RAG索引与应用缓存也可能保留旧资料；模型回答过时未必先由参数知识导致。先查实际送入模型的内容，再定位是哪一层仍旧。

## 8. 最小离线代码：TTL为正但内容已不一致

配套[cache_lab.py](examples/cache_lab.py)复用Agent的assess函数，只读取合成字典，不运行Redis或改价。输入有两份快照和明确参考时间，动作是时间/版本/金额比较，结果是报告。

核心摘录不能独立运行：

```python
result = assess(record, "2026-10-24T11:05:00+00:00")
print(result["origin_version_match"])
```

assess先检查时间线，拒绝未来证据；旧观测不支持当前价差。再确认产品相同、币种相同，用Decimal减金额；-2缺键不比较不存在的缓存内容。最后返回TTL投影和业务不一致提示，始终不执行失效动作。

完整运行前提Python3.12+及仓库。手动命令：

```powershell
cd H:\CodeX\Carreer\agent-industry-lab\runtime\publish-20261014
python knowledge-base/examples/cache_lab.py
```

其他读者替换cd目录。预期输出，本次未执行：

```text
projected_remaining_ttl_seconds: 180.0
origin_version_match: False
cache_minus_origin_price: -0.50
current_cache_presence: unknown
version_label_fixed_but_price_difference: -0.50
```

最后一行只把缓存版本标签改v2，仍保留8.50，因此金额继续不同。它说明“把版本字段改对”不等于重新生成了正确内容。这个改动只作用于本地复制的教学字典，不会接触任何真实价格。

## 9. 实验、错误与工程取舍

先纸笔预测三组变化：TTL改-1会出现no_expiry_recorded；改-2后不再计算缓存价差；as_of改晚到11:06:01，超过60秒教学新鲜度阈值，证据陈旧，价差为None。阈值来自本例策略，不是Redis规定。

出现Timezone required先核对真实时区，不能随手附UTC掩盖问题；Invalid price检查是否含NaN、负数或不支持精度；ModuleNotFoundError检查完整目录，不安装同名agent包。网络连接错误说明已超出离线例子，它没有Redis请求。

目前Agent只读元数据，未实现失效通知、原子版本检查、分布式锁或真实缓存适配。模型建议包含来源也不保证结论正确，人工需要核对工具报告。若后续接入真实服务，最小权限先只读，写入/清理操作另做业务授权与审计。

## 10. 课堂验收与答案

**一：TTL还180秒，是否价格一定最新？** 否。TTL是过期信息，来源可能已经更新。

**二：TTL=-2能证明商品已下架吗？** 否。只是该次查键未找到，源资料是否存在需另查。

**三：删缓存后还读到旧值，是否Redis没有删除？** 不一定，可能并发回填或另一个缓存层；先找请求与版本证据。

**四：版本相同、金额不同，能直接收费吗？** 不能。标记和数据矛盾先核查，且收费还要走权威结算流程，本例无此工具。

**五：把TTL设为1秒是否消灭所有一致性问题？** 否。并发与多层缓存仍存在，且回源压力显著改变。

交付一张“写v1→源改v2→读旧缓存”的时序图，以及TTL、版本、价格、观测时刻各能证明什么。能举出正TTL但旧内容的反例才算通过。
