# 第二十四讲｜一批原料用了到哪里？有向关系、队列与有限图遍历

前置第9讲关联键。关联[制造批次影响Agent](../examples/lot-impact-review/README.md)。学完能手推一次有向广度优先搜索，解释“候选、截断、真实全量”三者的区别。

## 1. 一张表为什么不够？

合成原料A进入混料B，B进入包装C，C进入发运D。调查A时，只查直接使用A的记录会找到B，却漏掉C、D。另一原料X也投入B，但X不是A加工产生的下游批次。

类比河流：从一个位置顺流查下游，不应沿另一条支流逆流回去。类比边界：制造关系可以分拆、合并、返工甚至有数据循环，不是自然地理；关系记录也未必完整，不能只看图就证明污染、缺陷或数量。

这里的业务问题是“哪些记录值得继续调查”，不是“哪些产品一定有缺陷”。今日Agent只做候选清单，处置、召回或通知都需要真实证据和授权。

## 2. 从记录到图

**图**由节点与边组成。节点是对象，这里为批次ID；边是关系，这里明确从投入指向产出。**有向**表示边有方向，A→B不自动意味着B→A。

程序用节点列表保存允许对象，用边字典保存from、to和source。source是关系记录的来源ID，帮助回查依据，不是证明记录本身绝对真实。

同一个批次ID出现两个不同实体会破坏结果，所以节点必须唯一；边端点不在节点清单中时，本例拒绝分析，不默默造出新批次。输入最多100节点和200边，限制一次任务规模。真实数据跨租户或跨工厂时，还需明确ID命名空间和访问隔离，本MVP没有那些接入。

小问题：节点名称相近是否就能连边？不能。边来自业务关系证据，不是模型按名字猜出来的相似度。

## 3. 为什么先组织邻接表？

**邻接表**记录每个节点直接指向哪些对象。原始边列表A→B、X→B、B→C，可以整理为A:[B]，X:[B]，B:[C]。

这样处理A时只看A的出边，不必每次从第一条记录重新扫描。对于小快照，普通字典与列表足够；并不因为用了图概念就必须安装图数据库。

邻接表中的边按目标ID与source排序，使同一份快照在多个等长路径存在时选择顺序稳定。稳定不代表业务因果更强，只是方便复核相同输入的结果。

## 4. 用排队的方式，一层一层查

**队列**像排队买票，先到先处理。广度优先搜索（BFS）就是先处理距离起点一条边的节点，再处理两条边的节点。这里每条边计一跳，不代表加工时间或距离相同。

从A开始：队列[A]、已发现{A:0}。取出A，发现B，标记B:1并放入队尾。取出B，发现C，标记C:2。取出C，发现D，标记D:3。若最多三跳，处理D时不能继续把E纳入已展开范围，记下D→E为截断边。

| 步骤 | 处理对象 | 新发现 | 队列变化 |
| --- | --- | --- | --- |
| 起点 | 无 | A，0跳 | [A] |
| 1 | A | B，1跳 | [B] |
| 2 | B | C，2跳 | [C] |
| 3 | C | D，3跳 | [D] |
| 4 | D | 记录到E的边界 | [] |

BFS在无权图中首次发现节点的跳数是最少边数。**无权**是本例不为边分配不同代价；不意味着关系没有业务意义。要比较运输时间、数量或风险，不能直接把跳数当最优业务路线。

## 5. 已访问集合为何能阻止无限循环？

如果有B→A，处理B又遇见A。程序先检查A是否已经发现；已发现则不再次入队。因此即使关系形成环，也不会A、B反复处理到无穷。

```python
if target in depths:
    continue
```

这是完整源码片段，不能独立运行。depths同时保存已发现节点和跳数；continue表示跳过当前这条边的后续扩展。

注意：遇到已发现对象不等于检测到了环。A→B、A→C、B→D、C→D中D会被重复遇见，但没有回到起点的环。判断有向环需要另外的算法或状态，本例没有实现“数据环诊断”。它只保证有限遍历。

## 6. 截断不等于查完，没截断也不等于真实全量

**跳数预算**限制沿关系走多远。三跳范围内结果B、C、D；D→E留在边界，意味着快照中已知还有未纳入的节点。报告必须包含hop_budget_truncated。

如果提高到四跳，当前快照可找到E，截断边可能为空。但真实系统里还可能有没采集到的记录、缺失工厂、延迟写入或错误关系。于是“当前快照无截断”与“真实范围已完整验证”是不同判断。

来源声明declared_complete=true只是来源自己的覆盖声明，不应被升级成独立验证。快照超过有效时间也要列限制。流程应分开数据覆盖、搜索预算和事实正确性，而不是统一返回一个含糊complete=true。

## 7. 保留证据路径，而不是只报一个数量

C的证据路径是A→B的source，再加B→C的source。报告可写path_sources=[edge-demo-01,edge-demo-03]，让审核者检查每一步。

当前代码每节点只保留BFS首次找到的一条最短路径，不枚举所有加工路径，不计算数量守恒、投入比例、库存或缺陷传播概率。同一个可达节点可能有多条独立来源，生产调查需要时再扩展证据结构，不能把单路径报告包装成全部证明。

另一个容易混淆的数量：visited_node_count包括起点A，candidate_lots不包括A。因此样例已访问4节点、候选下游3批次，都正确。若没写清口径，报表容易看起来矛盾。

## 8. 最小可复现实验

环境Python3.11+与完整仓库，无额外依赖/模型/网络。PowerShell进入仓库根目录：

```powershell
python --version
python knowledge-base/examples/lineage_bfs_lab.py
```

文件：[lineage_bfs_lab.py](examples/lineage_bfs_lab.py)，复用Agent函数。小图有A→B、B→C、X→B、B→A。按源码推导的预期，未执行：

```text
hops: 1 candidates: ['B'] cut: 1
hops: 2 candidates: ['B', 'C'] cut: 0
```

第一行只容许走一条边，B到C被截断；B到A因为A已发现，不导致反复入队。第二行多走一跳，C被纳入。X始终不在候选里，因为方向不允许从B逆查X。

找不到agent先核完整仓库与路径；Missing endpoint是数据契约问题，应补来源或修快照，不要自动给缺失批次填默认信息。

## 9. 逐段读代码与复杂度

```python
queue = deque([seed])
node = queue.popleft()
queue.append(target)
```

三个动作在完整函数中分别负责初始化、取队首、加队尾。Python标准库deque适合两端增删，普通列表反复删除头元素会搬移后续元素。这里不是用性能术语吓人，而是选择和排队动作相符的数据结构。

若节点数为V、边数为E，邻接表建好后，每个到达节点最多出队一次，每条相关边最多扫描一次，核心遍历通常记作O(V+E)。O表示规模增长趋势，不是实测秒数。本实现还排序邻接边、复制每条证据路径，整体额外成本不能忽略；最多100节点/200边和10跳正是明确的小范围约束。

本例保存路径会占更多空间，适合小图便于教学。大图可保存父指针，在需要时重建路径；业务需要全路径又会增加复杂度，需先明确问题再换基础设施。

## 10. 故障、选型与练习答案

| 现象 | 优先核查 |
| --- | --- |
| 其他原料被列下游 | 边方向是否被错误改成双向 |
| 一直重复A/B | 是否在入队前标记已发现 |
| 候选少于预期 | 跳数、缺边、快照范围或ID连接 |
| 无截断却仍查漏 | 来源覆盖不是搜索完整性 |
| 有source但结论不对 | 原始记录及建议是否真的被关系支持 |

1. 三跳找到D，可以说E没受影响吗？**不能。**E是边界之外，需继续核查。
2. 两条路径到D就是环吗？**不是。**重复到达和循环不同。
3. 可达是否证明有缺陷？**不证明。**只是关系支持的候选调查范围。
4. 需要图数据库吗？**这个固定小图不需要。**大规模、跨版本、并发查询再评估关系数据库递归/图引擎。
5. 源声明完整可以省人工吗？**不能自动省。**还需核来源、业务规则与处置权限。
