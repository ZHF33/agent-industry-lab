# 第二十六讲　收到一页成功响应，订单就导出全了吗？

本课讲分页采集的完整性证据。关联[分页导出审查Agent](../examples/export-page-review/README.md)。学完能手推游标链，并用终止、身份、快照与数量四项证据判断哪里需要补查。

## 1. 为什么数据要分批给？

想象仓库清点一本有多页的登记册。搬运一页容易，一次搬全册可能很慢。API也可能把很多记录分成小批返回。每批叫一页。一次请求成功只能证明这次通信收到结果，业务完整性需要后续记录。

纸册类比有一个边界。数据库在翻页期间可能继续新增或修改，页与页未必属于同一时刻。因此分页需要同时考虑顺序与数据版本。

## 2. 页码和游标的意思

页码常见为1、2、3。接口用页号和页容量选择范围。游标则是服务端给出的继续位置，可以是字符串。客户端应把它当协议令牌，按文档使用，避免猜测或自行加一。

真实接口可能在响应头给next链接，也可能在JSON里给next_cursor。不同接口有各自的结束规则。GitHub的官方分页说明以Link响应头为例。本课采用原创的小型游标契约，下一页为null才表示明确结束。

小问题：这一页只有一条记录，能直接停止吗？只有接口明确约定“短页即结束”才可如此。本课必须继续检查next_cursor。

## 3. 用四条记录推一遍

导出任务给出起点P0、快照SNAP-A和目标唯一记录数4。收集到的页面如下。

| 游标 | 记录ID | 下一页 |
| --- | --- | --- |
| P0 | ROW-1、ROW-2 | P1 |
| P1 | ROW-2、ROW-3 | P2 |

先从P0查起，记下来源page-A。随后查P1，记下page-B。再查P2时找不到页面，于是报告missing_page。ROW-2在两页出现，所以报告duplicate_records。原始条目数为4，唯一ID是1、2、3共3个，与目标4不同。

这里有三种不同问题。去重能处理重复计数，无法补出缺失的ROW-4。模型把结果说得更流畅也无法补出来源。

## 4. 为什么要记已访问游标？

如果P1又指回P0，简单的“取下一页”循环会不断重复。程序保存visited集合，每到一页先检查游标是否已经到过。重复则停止并报告cursor_cycle。

还需要最大页数。本例最多分析10页，即使游标每次都变，也会在预算耗尽时停止。预算终止应保留blocked_cursor，方便人理解停在哪里。它与业务结束是两种不同状态。

如果先收到P0和P2，而链条中缺P1，程序不会越过P1自行拼接P2。额外页面列为unused_cursors，人可以核对其来源。跳过断点可能掩盖缺失内容或串入另一批导出。

## 5. 快照为什么必要？

假设按时间倒序读订单。第一页读完后新增一条，第二次按偏移取“下一段”，旧记录的位置可能移动，造成重复或漏项。稳定排序、游标和服务端一致快照可以按具体接口减少这些问题，但名字叫cursor本身没有保证。

本例每页必须携带与导出定义一致的snapshot。发现不同立即报告并停止消费那一页的ID。来源声称相同快照，仍需核服务端是否真正提供一致读取。我们只审合成元数据。

数量也要写清口径。expected_unique是当前导出定义声称的唯一ID数。它的过滤条件、版本和记录身份必须一致。如果一条订单每次修改都产生版本，订单ID和订单版本ID可能对应不同数量。

## 6. 从输入到报告

完整源码中的片段如下，需结合完整文件阅读。

```python
if cursor in visited:
    reasons.append("cursor_cycle")
    break
```

cursor是当前继续位置，visited记录已经访问过的游标。break退出循环并保留原因。

```python
if page["next_cursor"] is None:
    terminal = True
    break
```

明确结束才设置terminal。即使terminal为true，重复ID、唯一数量差异和未链接证据页仍会被检查。不能把“到最后一页”自动升级成全部验收通过。

本例限制最多20份页面证据、每页100个ID。重复页面游标或来源ID会被拒绝，因为选择哪一份会产生歧义。重复记录ID则保留到报告中，帮助调查来源。

## 7. 离线实验

环境Python3.11+、完整仓库，无额外依赖。PowerShell进入仓库根目录后，手动运行[例子](examples/pagination_chain_lab.py)。

```powershell
python knowledge-base/examples/pagination_chain_lab.py
```

静态推导的预期如下，课堂脚本尚未执行。

```text
rows: 4
unique: 3
duplicates: ['ROW-2']
blocked: P2
terminal: False
```

修改P1为ROW-3、ROW-4并把next_cursor设为null，应得到终止且唯一数4。只把next_cursor改成null，重复与数量差异仍存在。这个单变量对照可验证“结束”和“数量正确”彼此独立。

找不到agent先检查完整仓库目录。Invalid page fields表示字段契约不符。Future evidence表示观察时刻晚于审核时刻，应核时间来源，避免通过修改审核时间掩盖问题。

## 8. 工程选型与故障处理

当前工具只审已经收集到的快照。真实采集器还需鉴权、请求超时、限流与重试。补采时应保留任务ID、快照、起点和成功落库范围，避免重启后从半页继续产生混合状态。

小批数据用内存映射足够。大量页面应分批持久化，记录游标检查点。断点恢复必须确认旧游标仍有效，不能假设所有API令牌长期可重用。真正发出next URL请求前，还需控制域名和凭据范围。本例工具参数仅接受当前export_id。

1. 已收4条、目标4条，为什么仍失败？重复使唯一数量只有3，且没有结束证据。
2. 有next链接但页面没收到，能写导出完成吗？应记录断链位置，等待补查。
3. 去重后数量正确就够吗？还需终止、快照与来源口径。
4. 最大页数到达后，怎样写状态？预算耗尽，保留当前位置和已收范围。
5. 分页一致是否证明记录内容真实？还需核原数据与业务规则。
