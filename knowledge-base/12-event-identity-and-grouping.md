# 第十二讲：收到四条告警，为什么不一定发生四次故障？

配合告警重复与噪声复核Agent。区分投递、事件和事故，

## 1. 快递通知重复响了两次

手机两次收到同一快递通知，不代表有两个包裹。系统间消息也可能重复投递。**投递**是收到一条记录；**事件**是它描述的那一次变化；**事故**是需要调查的业务故障。它们不是同一计数单位。

两个独立超时可能属于一个事故，也可能不同。模型看见同一个错误码，不能直接说“都是同一根因，可以静音”。生活类比只帮助理解重复通知，不替代真实监控系统的时间窗和因果分析。

小问题：四条记录是否等于四次故障？不等于。先核对事件身份，再讨论是否同一事故。

## 2. 事件编号是身份，分组键是分类

event_id用来指向一个事件。service/code/severity是本例分组键，表示服务、错误码、级别。身份相同且约定内容一致，可以视为同一事件的重复投递；身份不同即使分组键相同，也应保留为两个观察事件。

本例同一批次有E-1投递两次、E-2一次、E-3一次，共四条投递、三个独立编号。E-1与E-2都是demo-api的TIMEOUT/warning，归一组但计两个事件。E-3归另组。

身份的作用域必须明确：真实系统通常还要来源或租户。A平台的E-1与B平台的E-1不一定是同一事件。本例只处理固定合成批次，不实现跨租户或跨批次唯一性。

## 3. 同一编号内容不同怎么办？

可能源系统改写、版本混用、字段损坏，不能立即认定恶意。工具把编号列入conflicting_event_ids，并从正常分组统计中排除整个编号。人工要回源核对。

本例“内容”只有service/code/severity，不包括时间和描述。把这一点写清，避免读者以为程序比较了完整载荷。真实接入必须定义不可变字段、可更新字段和版本语义。

小问题：保留第一条、默默丢掉第二条冲突记录可以吗？不应。它会隐藏数据质量问题，必须留下冲突线索。

## 4. 代码逐步理解

说明片段，不可独立运行：

```python
ids[event_id] = payload
```

字典把事件编号映射到第一次看到的内容。再收到相同编号时，比较内容是否一致。同内容增加重复投递计数，不重复增加事件数；不同内容标冲突。

```python
Counter(payload for event_id, payload in ids.items()
        if event_id not in conflicts)
```

Counter是Python标准库的计数容器。输入是每个未冲突事件的分组键，不是原始投递列表。这样相同键的不同事件累加，而重复投递不放大。

如果把原始列表直接交Counter，计算的是投递次数；如果先set化分组键，得到的只是组种类，两个不同事件会被丢成一个。正确性取决于先定义你在数什么，不是选对一个库就结束。

## 5. 数字加不回去一定是错吗？

含冲突时，原始投递数、重复投递数与分组事件数不一定简单相加。本例重复数只记录与首条内容相同的后续投递；冲突记录既不算正常事件，也不包含在重复数中。UI应把冲突数量单列，不能强行用减法猜重复数。

如果业务需要严格守恒报表，应进一步定义“冲突投递次数”“有效事件数”等指标，并按互斥类别划分全部记录。本例没有提供完整守恒分类，不虚称完整告警运营统计。

## 6. Agent在流程里做什么？

模型查询批次、原始事件与规则，再调用分组工具。计算结果独立输出grouping_report，模型引用来源给调查建议。人工审核可以确认重复处理思路，但代码没有静音、关闭、路由或发通知工具。

这区别于第一讲幂等：本讲识别输入事件和统计口径，第一讲保护业务动作不重复执行。发现重复投递不意味着提交接口已经幂等；当前HTTP提交仍可能生成两个调查任务，需要独立设计提交去重。

## 7. 最小实验

Python3.12+，仅标准库，在仓库根目录执行：

```powershell
python knowledge-base/examples/grouping_lab.py
```

预期deliveries 4、unique_events 3、timeout_events 2。示例事件内容不冲突，先按事件编号去重，再统计类型。完整项目额外检查冲突。此次仅语法检查，预期不是实际运行结果。

逐行阅读：四条投递进入列表；dict按编号保留一份；Counter对唯一事件的类型计数；打印三种不同口径。不要把示例简化逻辑当作生产消息处理器，它没有持久化、并发和跨批次范围。

## 8. 故障与工程取舍

噪声数字突然翻倍：检查平台重投是否当新事件。不同事故被合并：检查把分组键当身份没有。同编号不同级别被丢失：检查字典覆盖是否隐藏冲突。服务重启又重复：进程内去重状态消失，需要持久事件身份存储和保留期限。

小批次标准库足够；大流量持续事件再评估队列、消费确认、持久去重、时间窗和过期清理。Redis只是存储工具，不会替你决定去重键。无限保留所有事件会持续占内存；过早过期又可能重复计数，保留策略必须根据业务延迟和审计需求选择。

## 9. 练习与解释性答案

一：同错误码不同event_id，是否删除一个？不应，它们是两个观察事件。

二：同event_id内容冲突，应认定哪个是真的？当前工具不做真实性判断，标冲突交人工回源。

三：分为一组是否证明同一根因？不证明，分组是分类，不是因果诊断。

四：approve能静音告警吗？不能，本例只记录接受建议。

五：换成数据库是否自动不重复？不会，仍需正确的身份键、约束和事件版本规则。
