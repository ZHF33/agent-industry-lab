# 第39讲 JSON 重名键与证据保全

## 一张抄表单上有两个峰档值

两名值班员在同一张表上分别写了“峰档 0 Wh”和“峰档 500 Wh”。如果抄到电脑时只保留最后一个值，复核员看到的表便像正常记录一样。即使两个值相同，也要先确认重复字段的来源。纸上还可看到划痕和批注，程序能否保留冲突取决于解析方式。此处处理的是一份数据对象内部的重名。不同日期的电量可以各自成记录，通过日期和档位联合识别。

**小问题**　原始文本里先写 0，再写 500。读出来的 500 能证明更晚的读数吗？

**解释**　文本顺序关系只说明哪个值写在后面，缺少测量时刻和修订记录。把后者覆盖前者会丢掉其中一个证据。

## 冲突在哪一步被抹掉

JSON 对象使用名字和值表示字段。键就是字段名。对文本 {"slots":{"peak":0,"peak":500}}，内层对象先可表示为有顺序的两对名字和值，第一对是 peak 与 0，第二对是 peak 与 500。Python 标准库默认解析时，普通字典只能保存每个键最后写入的值。此时得到的 peak=500 与只写一次的文本相同，后续数字范围检查无法看出差异。RFC 8259 要求提供方尽量保证对象内名字唯一，并说明有重名时各实现的行为可能不同。接收方可制定更严格的证据合同，遇重名退回来源。

Python 的 object_pairs_hook 是可选的解析回调，即在每个对象变为字典前，解析器把名字和值的列表交给指定函数。我们从空字典开始，逐对检查键。处理第一对后，peak 已经出现。处理第二对时触发异常，于是整份快照无法进入复核。回调对内层对象也生效。若两条合法记录来自数组，数组元素各自是对象，仍需根据业务身份验证是否重复。

**小问题**　把第二个 peak 改成 off_peak，结果怎样？

**解释**　键变得不同，重名检查通过。此时还必须检查两档是否都是该电表的合法费率档，以及电量是否为整数。

## 可重复实验

准备 Python 3.11 或更新版本。从仓库根目录运行 [示例](examples/duplicate_json_key_lab.py)。

```powershell
python knowledge-base/examples/duplicate_json_key_lab.py
```

脚本先用默认方法读取两份合成记录，再用带回调的方法读取。前一份只有一个峰档值，后一份只多加了一个同名项。回调逐项加到字典，先检查是否出现过。预期如下，本次仅静态审查和手推。

```text
default 500
checked 500
default 500
rejected duplicate peak
```

提示文件不存在时，检查是否在仓库根目录。若重名输入仍出现 checked 500，检查是否先解析成普通字典再交给回调。回调必须参与原始 JSON 文本的解析。

## 工程取舍与练习

[分档电量费用复核 Agent](../examples/energy-charge-review/README.md) 在打开合成抄表快照时检查重名，然后检查电表范围、档位和整数电量。一次图运行只读入一个快照，使各次工具引用同一份数据。已给出零电量仍参与核算，缺档留作待补。当前检查仅覆盖这份计量文件，服务的其他 JSON 入口由框架按自己的规则解析。接真实台账时，应统一入口规则，保留原始来源和错误诊断，并核对快照对应的结算周期。重名检查也不解决 JSON 数组中重复行或其他格式的重复列。

练习：把样例改成 {"first":{"peak":0},"second":{"peak":500}}。会拒绝吗？答案是不会，两个 peak 分属不同对象。若 first 和 second 被业务系统映射成同一电表、同一结算时段，需要再查业务主键。
