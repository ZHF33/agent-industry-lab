# 第三讲：Agent 做到一半，怎样停下来等你审核？

这篇讲义配合库存盘点 Agent，讲解状态、检查点与人工审批。

## 1. 从仓库桌上的文件夹开始

账面100件，盘点94件。调查员先看库存表，再查出库单，把结论交主管。主管正在开会，调查不能直接调整库存。最自然的做法是把资料放进一个带编号的文件夹，写上“等审核”，明天拿回原文件夹继续。

程序也需要类似文件夹：记录输入、已经查过的资料、计算结果、下一步。这就是**状态**，意思是“任务此刻记住的内容”。它不是一个简单的成功/失败标签。`status="waiting"`只能说明正在等，不能找回究竟等哪份建议。

类比边界：纸质文件夹关灯后仍在桌上；程序内存随着进程退出就消失。因此“有状态”不等于“重启也能恢复”。本仓库示例选择内存，适合演示暂停流程。

小问题：只记一个“待审核”标签够不够？答案：不够，还要知道任务编号、建议、证据及下一步，否则主管不知道审核什么。

## 2. 三个容易混淆的概念

**状态**：任务记住的内容。**检查点**：执行到某个位置时保存的一份状态，像游戏存档。**任务编号**：找回这份状态的钥匙。LangGraph把它叫thread_id，这里是一条任务的编号，不是聊天窗口编号。

假设两种商品都在等审核。如果没有不同编号，就可能把甲商品的审批恢复到乙商品。接口为每次提交生成随机UUID（一种低碰撞概率的编号），随后所有审核都使用同一个thread_id。

编号不是密码。知道编号并不应该获得审批权限。本例还检查API密钥；真实多用户系统仍需核对用户身份、所属仓库与审核权限。不能把“请求里写了王主管”当作身份认证。

## 3. 为什么需要图，而不是一个很长的函数？

图在这里不是图片文件，而是执行步骤和连接关系：

```text
输入初始化 → 模型判断 → 工具查询 → 再交模型判断
                           ↓
                     有建议与来源 → 人工审核 → 结束
```

**节点**是一段做具体事情的代码；**边**决定下一段代码去哪。模型节点返回route=tools就去工具节点，返回route=review就去审核节点。模型如果漏了来源，程序增加反馈后再进模型节点。四轮限制防止一直循环，业务失败明确报错。

这并不意味着LangGraph替你决定建议正确。图管执行顺序，业务校验仍由代码和人工承担。库存数量让计算工具算，模型只能解释；待入账-6件与盘差-6件相等，也不证明它们属于同一次作业。

## 4. 代码拆开看：先保存，再暂停，再恢复

以下是概念片段，不能单独运行；完整入口在 `examples/inventory-discrepancy/graph_agent.py`。

```python
graph = builder.compile(checkpointer=InMemorySaver())
```

输入是已经定义节点和边的builder。动作是编译图并配置内存检查点。结果是可执行的graph。InMemorySaver把检查点保存在当前程序内存，不创建SQLite文件。选择它能保持源码精简，但服务退出后不能恢复旧任务。

```python
config = {"configurable": {"thread_id": "一个任务编号"}}
graph.invoke({"ticket": input_data}, config)
```

输入是业务资料与任务编号。invoke表示“执行图”。执行完成可能是结束，也可能是暂停；HTTP请求返回不代表审核已完成。接口的pending_review用于告诉调用者下一步仍需人工。

```python
decision = interrupt({"result": state["result"]})
```

interrupt表示“在这里把待审核资料交出去，并暂停”。第一次到这里不会立刻得到decision。状态被保存，程序把审核材料返回调用者，等待下一次请求。它不是不停占着线程睡觉，也不是给主管自动发消息。

```python
graph.invoke(Command(resume={"decision": "approve", "reviewer": "demo"}), config)
```

第二次用同一个编号调用。Command表示恢复指令，resume提供人工答案。图恢复审核节点后，interrupt返回这个答案。代码检查approve/reject和审核人，再形成结果。approve只表示接受建议，本项目没有库存调整工具。

关键细节：恢复时中断节点会从头重新执行。中断前如果扣库存、发邮件，恢复可能重复做一次。因此审核节点中断前只整理数据，不做外部业务操作。这是设计约束，不是靠提示词保证。

小问题：恢复时重新生成thread_id可以吗？答案：不可以。新编号找不到原来暂停的检查点，相当于拿错文件夹。

## 5. 不开模型也能学习的最小实验

配套 `knowledge-base/examples/state_lab.py` 使用标准库字典演示状态保存和编号查找，**不是LangGraph实现**，也不模拟真实模型。这样先理解最小概念，不必安装框架。

前提：已安装Python3.12+。在仓库根目录执行：

```powershell
python knowledge-base/examples/state_lab.py
```

预期打印 waiting_review、reviewed、restart_lost。第一步是保存待审核状态，第二步同编号恢复为已审核，第三步清空内存后找不到旧任务。这些是预期输出，本次只做语法审查，不提供虚构的执行结果。

实验中copy防止外部字典修改立即影响保存状态。真实检查点还需要序列化、版本与并发控制；这个简化实验没有这些能力。

## 6. 常见故障：先找断在哪一层

1. 404找不到任务：编号错误，或API服务已经重启。查看调用者保存的thread_id，不要为了“修好”随便新建。
2. 409不能审核：任务不是待审核，可能已经审核过。重复审批应明确拒绝，不静默重新执行。
3. 401密钥错误：n8n的X-API-Key与服务配置不一致。密钥放凭据管理，别写工作流JSON。
4. 429服务忙：示例串行处理。等待后是否重试要结合业务语义；网络响应不确定的提交不能盲目重试，否则生成两条调查。
5. 图超过轮数：模型反复调用工具或不引用来源。检查提示和工具契约；无限增大上限只会隐藏问题。
6. Docker里127.0.0.1连不上：这个地址指容器自己。改成API实际可达地址，不能通过关闭全部防护解决。

## 7. 内存、数据库和队列各解决什么？

内存检查点简单，适合一台机器、一个进程的短期演示。数据库检查点解决重启后找回状态，但需要访问权限、数据清理、备份和恢复验证。任务队列解决长任务与并发等待，不能代替保存审核状态；数据库也不会自动替你处理HTTP请求排队。

不要一上来全部安装。先确认业务要求：是否跨天审批？是否多实例？是否允许任务丢失？跨天审批通常不能只依赖内存。库存示例明确只保留进程内状态；以后换持久检查点需要调整依赖与运行配置，不只是改一个名字。

## 8. 课堂练习与答案

练习一：主管批准建议是否应立即调整-6件库存？答案：不应。建议认可和财务/库存调整是不同授权，需独立审批、证据与幂等写入流程。本例根本不提供该写工具。

练习二：启动两个API worker能提高容量吗？答案：可能增加执行进程，却让内存检查点分散。提交在进程A，审核到B会找不到任务。先使用一个worker，规模化时改共享持久状态及合理并发。

练习三：检查点保存了，是否一定能恢复得安全？答案：不能。中断节点重跑、工具副作用、身份权限和依赖变化仍会影响安全；检查点只是恢复机制的一部分。

练习四：把原始运行轨迹上传GitHub是否方便审核？答案：本系列只上传合成源码与脱敏检查摘要。轨迹可能含真实业务资料，应留在受控环境。
