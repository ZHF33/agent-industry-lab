# 第一讲：点了两次“提交”，为什么不能处理两次？

这是面向零基础读者的正式讲义。按零基础讲解，不要求先懂 HTTP、API、数据库或 Python。先读下面的入门部分；理解以后，再继续后面的技术讲解。没有准备好电脑环境时，可以先读概念，不必立即运行代码。

## 入门：先从点外卖开始

你点了一份面包，点击“下单”，页面一直转圈，最后显示“网络超时”。你又点了一次。

你只想买一份。但商家可能收到两份订单，做两份面包。

为什么会这样？第一次发送以后，至少有两种可能：商家没有收到；或者商家已经收到并记下订单，但手机没有收到确认消息。

**超时表示“我等不到回信”，不能证明“对方没有做”。**

先停一下：如果商家已经记录订单，只是回信途中丢失，手机是不是仍可能显示超时？是。这就是为什么不能把所有超时都直接当成失败。

本课只借用下单理解重复操作，不讨论真实支付和退款机制。

### 把生活里的角色换成软件里的名字

| 名字 | 先这样理解 | 本项目里的对应物 |
| --- | --- | --- |
| 客户端 | 提出需求的一方 | 操作页面或 n8n |
| 服务端 | 接收并处理需求的一方 | 审核服务 |
| 请求 | “请帮我做这件事”的消息 | 提交一份文案 |
| 响应 | 处理方发回的消息 | 返回报告或错误 |
| API / 接口 | 双方约定的办事窗口 | /reviews 审核入口 |
| 数据库 | 服务保存记录的账本 | 本地 SQLite 文件 |
| JSON | 用字段名和值组织数据的文本格式 | 文案、商品信息、任务编号 |
| HTTP | 发请求、收响应的一套通信规则 | 页面和服务之间的通信 |

不需要先背英文。先知道谁发消息、谁处理、哪里保存记录。

n8n 可以理解成自动办事的助理：收到需求，调用审核服务。助理再打一次电话，服务也需要知道是不是同一件事。

### 第一招：给这一次提交一个编号

我们给一份文案的第一次审核取一个编号：bread-review-v1。第一次发送带上这个编号；超时以后再试，仍然带同一个编号。

服务查账本：没见过编号，就处理并保存；见过编号且内容一样，就拿出已保存的报告；编号一样但内容变了，就拒绝旧编号，要求创建新版本。

| 你在做什么 | 编号 | 内容 |
| --- | --- | --- |
| 第一次提交 | bread-review-v1 | 文案 A |
| 超时后再试 | bread-review-v1 | 文案 A |
| 修改后重新审核 | bread-review-v2 | 文案 B |

编号在代码里叫 job_id：job 是任务，id 是编号。编号标识一次业务提交，不是每次点击或每次网络尝试。

现在认识“幂等”，读作 mì děng：同一个业务任务重复提交，不再增加相同的业务效果。可以先记成：**同一张单，可以问多次，但不要多做一份。**

程序仍会收到第二次消息、查询记录。这不表示程序绝对只运行一次；我们关心的是有没有重复创建业务结果。

### 第二招：编号之外，还要检查内容

假设第一次用 bread-review-v1 提交“今日新鲜出炉”，第二次却用相同编号提交另一份文案。只认编号会返回旧报告，造成新文案误用旧审核。

所以还要比较内容。项目把输入转换成一串固定长度的字符，用来进行比较，这叫摘要。可以理解成内容的校验标签。

这个类比有边界：摘要不是身份证、不是密码，不能证明是谁提交了内容。项目使用 SHA-256 算法；先理解“用它检测内容是否变化”，以后再看计算代码。

| 账本里有没有编号 | 内容是否一致 | 该怎么做 |
| --- | --- | --- |
| 没有 | 不需要比较 | 创建报告 |
| 有 | 一致 | 返回已保存报告 |
| 有 | 不一致 | 拒绝旧编号，要求新版本 |

### 两个人同时查账本，又会怎样？

第一位工作人员查：“没有记录。”还没写进去，第二位也查：“没有记录。”于是两个人都开始处理。

多个任务的执行时间互相重叠，叫并发。问题不是忘了查，而是查询和保存之间插入了另一次处理。

当前审核很短，项目用 SQLite 的写事务协调：第一位获得写入资格，完成查询、比较和保存，再结束；第二位等待以后重新查询，看到已有记录就复用。等待太久仍可能失败。

它协调的是数据库写事务，不是让整台电脑只运行一个程序，也不是阻止所有读取。

### 第三招：相关记录要一起成功

人工拒绝文案时，需要改报告状态，还要保存“谁拒绝、为什么拒绝”。只做好一步，账本就不完整。

事务把相关数据库变化放在同一次提交里：成功时一起确认，出错时撤销尚未提交的变化。

提交 commit：确认保存本次变化。回滚 rollback：撤销当前事务尚未提交的变化。回滚不会把整份数据库恢复到昨天。

幂等回答“同一任务又来一次怎么办”；事务回答“这一组数据库变化怎样一起成功或撤销”。每次给新编号，两次事务仍可能各自成功，因此事务不自动去重。

### 最后才讨论：什么时候可以再试一次？

重试就是再尝试。网络临时故障可能可以重试，材料缺字段则应该先补齐，旧编号配新文案则应该先确认版本。

| 看到的结果 | 含义 | 下一步 |
| --- | --- | --- |
| 网络超时 | 没收到结果，执行情况不确定 | 用稳定编号再试，或先查询 |
| 422 | 输入不能按接口要求处理 | 看错误说明，修正材料 |
| 409 | 与已有任务或决定发生冲突 | 查当前状态，判断是否新版本 |
| 200 | 本次请求处理成功 | 读返回结果 |

200、409、422 是接口响应的状态码。数字要结合错误说明理解；409 不总是“内容改变”，也可能是已经审批过。

不要无限重试：服务可能持续忙，错误输入不会自己变正确，模型调用还可能增加费用。等待逐渐变长叫退避，加随机等待错开高峰叫抖动。后面再解释具体策略。

### 三道小题，检查自己有没有理解

1. 超时后换新编号再试，好不好？通常不好，因为第一次可能已成功，新编号会创建另一项任务。
2. 改了文案还沿用旧编号，好不好？应按契约创建新版本，避免误用旧报告。
3. 数据库最后只有一份报告，就一定只调用过一次模型吗？不一定，两次计算可能在保存之前都已经发生。

还有一个重要边界：数据库事务通常管不到另一家公司提供的发送服务。本地只有一行记录，不代表外部通知、模型费用或订单效果只有一次。

## 一、从一个看似普通的超时开始

运营人员提交一份面包宣传文案。n8n 把请求发给审核服务，服务生成报告，报告要经过人工审批才能进入后续操作。

正常情况下，链路是：收到请求 → 校验输入 → 生成报告 → 保存报告 → 返回响应。

现在假设 n8n 等待五秒后超时。运营人员看到失败提示，点击“再试一次”。你能判断第一次请求到底完成了哪一步吗？不能。至少存在以下几种可能：

| 服务实际经历 | 客户端看到 | 再次请求的风险 |
| --- | --- | --- |
| 请求没有到达服务 | 超时 | 需要再次提交 |
| 服务收到请求，尚未保存结果 | 超时 | 两次请求可能同时执行 |
| 服务已经保存，响应在途中丢失 | 超时 | 可能重复创建报告 |
| 服务已经完成外部业务动作，尚未记录完成状态 | 超时 | 可能重复发送或发布 |

客户端观察到的超时，只能说明“在等待期限内没有拿到可用响应”。它不能证明服务没有处理，也不能证明外部动作没有发生。

这是本讲的起点：网络失败造成的是**结果不确定**。重试可以提高最终完成的机会，但如果系统不识别重复请求，重试也会放大副作用。

把审核报告换成生成图片、创建订单、发送客户通知，道理一样；只是重复操作的成本越来越高。

## 二、先把三个概念分开

### 2.1 幂等：重复执行不再增加相同业务效果

数学表达是 f(f(x)) = f(x)。理解工程场景时，关注的是业务状态，而不是代码到底运行了几次。

“把任务状态设置为 approved”重复执行，通常仍是 approved；“再增加一条审批日志”重复执行，则会产生多条记录。这两步放在同一个接口里，接口是否幂等就需要整体判断。

因此，不能仅凭请求用 POST 还是 PUT 判断实现一定正确。HTTP 方法表达语义，但实际数据库写入和外部调用仍由代码决定。

本项目采取的策略是：同一个 job_id 代表同一次审核提交。重复输入复用报告，不再新增报告；同一个 job_id 携带不同输入则拒绝。

还要注意：幂等不要求每次响应字节完全相同。当前代码在审批后会更新报告状态，重新提交相同审核输入时，返回的是当前已保存的报告，可能已经从 pending_review 变成 approved。业务上没有再次创建审核任务，但它不是“永远重放第一次 HTTP 响应”的实现。

### 2.2 事务：让一组数据库操作共同成功或撤销

例如人工审批包含两次写入：更新报告状态、插入审批记录。如果只完成第一步，系统显示“已批准”，却没有审计记录；只完成第二步，也不一致。

事务为这组数据库变化提供共同的提交边界。遇到错误时回滚，成功时提交。它保护的是被纳入同一事务的数据库操作，不会自动包含另一台服务器上的邮件发送或模型请求。

### 2.3 重试：再次尝试一次可能失败的操作

重试是调用策略，幂等是重复操作的业务约束，事务是数据库变化的执行边界。三者需要配合：重试负责再次尝试，幂等识别是否同一任务，事务维护判断与写入的一致性。

只加重试，可能重复业务；只加事务，每次重复请求仍可能各自成功；只在内存里记录任务 ID，进程重启后记录又会丢失。

## 三、怎样给一次业务提交一个稳定身份

### 3.1 job_id 应该标识什么

标识的是一次有业务意义的提交。例如“某份文案的第一个审核版本”。

重试时沿用原来的 ID；文案真的修改了，生成新的版本 ID。不要在每次 HTTP 请求节点执行时重新生成随机 ID，否则每次重试都会变成服务眼中的新任务。

也不要只用旅客姓名、商品名称或 PNR 作为永久任务身份。一个旅客可能有多次处理，一个商品有多版文案，同一个 PNR 也可能经历修订。任务身份需要纳入版本或提交批次。

在多租户产品中，“店铺 A 的 demo-001”和“店铺 B 的 demo-001”应是两项独立任务。数据库可以使用 tenant_id 与 job_id 的组合唯一约束；服务先从认证上下文确定租户，不能直接相信请求正文声称的租户身份。

### 3.2 为什么还要保存输入摘要

如果服务仅检查 ID，调用者误用了旧 ID，系统可能返回旧文案的审核报告。调用者以为新文案审过了，实际上拿到旧结果。

因此需要保存输入摘要 digest，回答“这个 ID 原来对应的内容，和现在是否一致”。项目代码先对经过 Pydantic 校验的数据做序列化，再计算 SHA-256：

```python
digest = hashlib.sha256(
    json.dumps(
        body.model_dump(), sort_keys=True, ensure_ascii=False
    ).encode()
).hexdigest()
```

逐项看它的作用：model_dump 得到解析后的字段，sort_keys 稳定字典键顺序，ensure_ascii=False 保留 Unicode 字符表示，SHA-256 得到固定长度摘要。

但这不是所有系统通用的“语义相同”判断：列表顺序变化会改变摘要，字符串空格变化也会改变摘要，Unicode 的不同编码形式也可能不同。是否把这些变化视为同一业务输入，需要契约提前规定，不能随意归一化旅客姓名后把重要差异抹掉。

本项目采用精确的解析后输入匹配，适合小型审核接口。生产接口还要决定哪些字段纳入摘要、时间戳等非业务字段是否排除、提示词和规则版本如何固定。

摘要不是加密，也不是访问凭据。它不能防止未授权的人访问报告，更不能代替租户隔离。

## 四、把“查有没有”和“写进去”放到并发环境

先看一个常见错误思路：查询任务 ID，不存在就计算结果并插入。单人演示时很好用，但两个请求同时到达就会出问题。

| 时刻 | 请求 A | 请求 B |
| --- | --- | --- |
| 1 | 查询 ID，没找到 | |
| 2 | | 查询相同 ID，也没找到 |
| 3 | 生成报告 | 生成报告 |
| 4 | 插入成功 | |
| 5 | | 插入时触发主键冲突 |

主键确实保护了数据库不出现两条相同 ID 的记录。但如果生成报告需要昂贵模型调用，两次费用可能已经发生；如果中间还发送通知，通知可能已经重复。

“数据库最后只有一条记录”和“业务动作只发生一次”是不同保证。

### 4.1 当前代码为什么使用 BEGIN IMMEDIATE

当前审核计算是很短的本地规则检查，所以可以在短事务内完成：

```python
with sqlite3.connect(db_path, timeout=10) as db:
    db.execute("BEGIN IMMEDIATE")
    existing = db.execute(
        "SELECT digest, report FROM reviews WHERE id=?",
        (body.job_id,),
    ).fetchone()
    # 比较输入；已有则复用，否则生成并插入
```

BEGIN IMMEDIATE 会尝试立即开始写事务。SQLite 同时只允许一个写事务；别的连接正在写时，这一步可能等待或报忙。于是 A 获得写事务后进行检查与插入，B 要等 A 结束，才重新查询并看到已经保存的报告。它序列化的是写事务，不只是同一个 job_id。[SQLite 事务说明](https://www.sqlite.org/lang_transaction.html)

timeout=10 是数据库锁等待相关的连接参数，不是 HTTP 请求总超时，也不是模型超时。服务锁等待十秒，而客户端只等五秒时，客户端仍可能先超时。

这种方案以降低写并发为代价，换取简单的本地一致性。不要把它照搬成 PostgreSQL 所有任务共享一把大锁，也不要在锁内进行持续几十秒的模型推理。

### 4.2 return 以后，会不会没提交

在 Python 的 with 块里 return，仍会先执行上下文退出流程。现有默认事务控制方式下，正常离开连接上下文会提交，出现异常则回滚。return 并不绕过这一流程。

但“连接上下文”不等于“关闭连接”。sqlite3 的上下文管理器负责事务处理，不负责 close。现有源码没有显式关闭连接，教程需要诚实指出这个资源管理缺口。改进可使用 contextlib.closing 包住连接，再在内层 with conn 管理事务；本讲不把建议改进冒充已经修复。[Python 3.12 sqlite3 文档](https://docs.python.org/3.12/library/sqlite3.html)

同样，SQL 用 ? 参数绑定数据，不能通过字符串拼接插入用户值。本项目遵循这一点。

## 五、逐步读懂现有审核接口

数据库 reviews 表有三个核心字段：id 是任务身份，digest 是原始输入摘要，report 是保存的 JSON 报告。

处理逻辑有三条分支：

| 数据库状态 | 本次输入 | 处理 |
| --- | --- | --- |
| ID 不存在 | 校验通过 | 生成报告并插入 |
| ID 已存在 | 摘要相同 | 返回当前保存的报告 |
| ID 已存在 | 摘要不同 | HTTP 409，要求新版本 ID |

读取已有结果时，不再调用 review。报告在审批以后会更新状态，但原始 digest 保留，用来维持提交身份。

再看人工审批：读取报告，确认没有阻塞问题，确认状态仍是 pending_review，然后更新状态并插入决定记录。两次写入在一个事务中。已经审批过的请求再次提交决定时返回 409。

这个审批接口采用“终态禁止再次写入”，而不是“相同审批决定自动返回成功”的重放策略。因此审批响应丢失后，客户端应先查询报告状态进行确认，不能把每个 409 都当成审批没有成功。

最后，审核通过不等于文案语义已验证。当前 Skill 主要检查结构化事实、声明引用和字符限制，返回 semantic_verified=False；完整文案仍由人审核。幂等保证重复提交的处理方式，不会提高规则本身的判断能力。

## 六、动手实验：先观察现象，再解释原因

配套 [实验代码](examples/idempotency_lab.py) 只调用本地测试客户端，不启动外部服务，不访问真实旅客或店铺数据。实验在隔离子进程中运行，进程退出后清理临时数据库，避免现有 API 未显式关闭的连接阻止 Windows 删除文件。这是实验隔离措施，不代表已修复服务连接管理。

从仓库根目录运行：

```powershell
.\.venv\Scripts\python.exe knowledge-base/examples/idempotency_lab.py
```

实验做五件事：

1. 用同一输入提交两次，断言响应相同，并直接查询数据库，确认只保存一条报告。
2. 修改文案而保持 ID，断言 409；确认原始报告没有被新输入覆盖。
3. 记录人工拒绝决定，创建一个新的应用实例连接同一数据库；确认决定保留。这里只模拟应用重新初始化，不是完整操作系统或进程崩溃实验。
4. 插入一条实验数据后主动抛出错误，回滚事务；确认数据不存在。
5. 使用两个独立数据库连接并发争抢同一任务，BEGIN IMMEDIATE 序列化判断；确认一个创建，一个复用，最终只有一行。

并发实验验证的是本地 SQLite 算法边界，不是 n8n 实机压测，也不是分布式 exactly-once。一次通过说明样例场景符合预期，不能证明所有故障场景均已覆盖。

读输出时请主动回答：哪一个断言检查了响应？哪一个检查了真实数据库状态？为什么只比较返回值不足以证明没有重复记录？

## 七、重试应该怎样设计

先确认操作可安全重试，再讨论重试次数。否则加大重试次数，只会加大重复业务的机会。

| 现象 | 建议策略 | 原因 |
| --- | --- | --- |
| 输入字段不合法，422 | 修改输入，通常换新版本 | 相同无效输入再试不会变有效 |
| 相同 ID 不同内容，409 | 查询旧任务或使用新版本 ID | 这是业务冲突，不是网络抖动 |
| 已经有审批决定，409 | 查询当前状态 | 之前的决定可能已经成功 |
| 请求超时、连接中断 | 有幂等保护时有限重试或查询 | 结果不确定 |
| 429、部分瞬时 5xx | 按服务约定有限重试 | 可能暂时过载；并非所有 5xx 都可恢复 |
| 外部动作完成与否不明 | 优先对账或人工处理 | 无可靠外部幂等键时不能盲目重复 |

一个教学策略可以是：总尝试次数最多四次，第一回立即发送，失败后分别在递增等待范围内抽取随机延迟；设置总体时间预算。这里的“最大四次”包括第一次，不能写成四次重试后又多出一次。

指数退避降低持续压力，随机抖动减少大量任务同时恢复时再次一起冲击服务。有 Retry-After 的服务要遵循约定，同时受总体预算限制。具体次数和等待不是标准答案，需要结合业务期限、服务限流和成本。

还要数清重试层级。如果 n8n、API 客户端和模型 SDK 都各自允许三次尝试，模型最多可能被尝试 27 次。各层重试乘起来，会放大流量与费用。应明确谁负责哪一种失败，避免层层兜底。

重试次数、最后错误、任务 ID、工具或模型版本、耗时要进入日志；日志只记录必要脱敏信息，不保存完整客户文档。

## 八、长时间模型任务为什么不能照搬短事务

假设审核以后改成调用模型，平均需要三十秒。把模型调用放在 BEGIN IMMEDIATE 后面，等于模型思考期间一直占着写事务，其他任务也难以更新。

可拆成三段：短事务登记任务并领取 → 事务外调用模型 → 短事务保存结果。

这时必须增加状态，例如 received、running、succeeded、failed、needs_review，以及领取者、租约到期时间和尝试记录。并发领取要用数据库支持的原子操作实现，不能只是普通查询后改状态。

但拆段以后又出现一个问题：模型完成，工作进程在写结果前崩溃。恢复者可能重新调用模型。任务状态解决的是调度与恢复，不会自动保证模型只被计费一次。还要考虑供应商是否支持幂等、是否能查询已有请求、是否接受重复计算。

LangGraph 检查点能帮助保存执行状态，n8n 能安排流程重试，Dify 能管理工作流；这些编排能力仍要依赖业务接口提供的身份与副作用控制。节点变成可视化，不会消除不确定性。

## 九、为什么数据库事务保护不了发送通知

考虑两种顺序：

先发送再保存，发送成功但保存失败时，重试可能再次发送。

先保存“已发送”再发送，保存成功但发送失败时，系统可能永远认为已经完成。

把两步放进一个 Python 函数没有解决原子性，因为数据库和通知服务并不共享本地 SQLite 事务。

一个常用工程方案是 transactional outbox：在同一数据库事务里，保存业务变化和“待发送事件”。独立工作进程读取事件并发送，完成后标记状态。这样业务提交成功却丢失发送意图的问题更容易控制；事件发送仍可能重复，接收方需幂等消费，或按外部事件 ID 查询、去重。[AWS outbox 模式资料](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

如果目标平台既没有幂等键，也没有可靠查询接口，而重复发送不可接受，就需要人工对账或改变业务流程。不能给这种系统写上“exactly-once”就认为已经解决。

本仓库当前审核 Skill 没有实现 outbox。Bakery 本地发布记录也不等于真实社交平台发布。本段是下一阶段架构说明。

## 十、从原型迁移到工程系统，需要补哪些判断

| 条件 | 应考虑的演进 | 不能误解的地方 |
| --- | --- | --- |
| 单机、短规则任务 | SQLite + 短事务 | 仍需连接管理、错误处理和测试 |
| 较高写并发、多服务 | PostgreSQL + 明确约束与隔离策略 | 换数据库不自动得到幂等 |
| 耗时模型调用 | 队列、领取状态、租约、检查点 | 可能仍有重复计算 |
| 查询开销较大 | Redis 缓存 | 缓存丢失不能导致业务身份丢失 |
| 真实发送、发布 | 外部幂等键、outbox、对账 | 本地成功记录不等于外部成功 |
| 多租户、隐私数据 | 认证授权、隔离、最小日志 | job_id 和摘要不是权限凭据 |

任务记录保存多久也有业务影响。清除记录以后，旧请求重放可能被视为新任务。应规定允许重试的窗口、任务与修订关系、记录保留和撤销流程。不能为了节省存储随意清空去重记录。

锁等待失败要映射成明确的服务错误；模型和规则升级要明确任务版本；长时间任务需要状态查询接口。所有这些都应该写进接口契约，让调用方知道怎样恢复。

## 十一、课堂练习与参考答案

**练习一：每次 n8n 重新执行都生成新 UUID，服务还算有幂等保护吗？**

服务对单个 UUID 可能实现了幂等，但调用方每次换身份，无法保护同一逻辑任务。应在提交时生成并持久化，重试沿用。

**练习二：两个相同请求都调用模型，只有一个结果成功插入，是否完成了去重？**

去重了保存记录，没有去重模型调用。要区分存储、计算、费用和外部业务效果各自的边界。

**练习三：相同输入在人工审批后再次提交，为什么报告状态不同？**

当前接口复用的是可变任务报告，而不是不可变首次响应。需要当前状态时这是合理契约；若客户端要求首次响应重放，则需另存原始提交响应或拆分提交与查询接口。

**练习四：发生 409 就换一个随机 ID 重试，是否可行？**

不能无条件这么做。若是内容修订，可以新建版本；若是已经审批成功，换 ID 会创建重复任务。先读错误原因、查询当前状态。

**练习五：开启 Redis 分布式锁以后，就能放心自动发布吗？**

不能。锁可能过期、进程可能崩溃，外部服务的完成状态仍不确定。需要任务身份、持久化状态、外部去重和恢复策略一起设计。

## 十二、对现有代码的审查结论

已具备：任务主键、输入摘要、短写事务、同 ID 输入冲突、人工决定不可覆盖、持久化报告。

需要明确的边界：报告随审批变化；审批决定重复提交返回冲突；没有模型语义验证；没有真实工作流平台联调证据；没有外部 exactly-once 保证。

建议后续改进：显式关闭数据库连接；明确锁等待错误的 HTTP 映射；增加多租户身份与认证；补业务级并发和故障注入测试。模型任务变长后再演进到领取状态与队列，不把短规则事务扩成慢速外部事务。

读完本讲，应能沿着“任务身份 → 输入匹配 → 原子判断与保存 → 重试策略 → 外部副作用边界”解释自己的 Agent。解释清楚这条链，比只列出采用了几个框架更能证明系统可恢复、可审核。
