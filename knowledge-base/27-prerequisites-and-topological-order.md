# 第二十七讲　前置任务没完成，为什么不能直接按清单顺序开工？

本课面向刚接触工作流的读者。配套[生产任务依赖审查Agent](../examples/task-dependency-review/README.md)。学完能画出前置关系、手推拓扑顺序，并区分结构可行、当前就绪和实际派工。

## 1. 清单顺序为什么可能错？

一个合成工厂任务表写着包装、备料、装配。若直接从第一行执行，包装可能早于装配。我们需要表达业务约束，而不只是给任务编号。

生活类比是做饭。先洗米再煮饭是前置关系，摆盘可与部分准备工作并行。类比边界在于真实工厂还有设备、人力、物料、安全与授权。依赖审查只解决其中的先后条件。

**前置任务**是某任务开始前需要满足的任务。**依赖图**用节点表示任务，用有向边表示前置指向后续。A→B表示B依赖A。节点的业务状态另存为pending、running、done，本例分别代表待处理、进行中、已完成。

## 2. 把方向写清楚

标准库TopologicalSorter接收的映射是“任务→前置集合”。例如B:[A]表达A先于B。它与画图时A→B的视觉方向不同，但语义相同。把映射误写成“任务→后续”，得到的顺序就会颠倒。

本例要求前置ID都在任务表里。库本身可以把仅出现在前置集合的节点加入图，而业务审查需要该对象的明确状态，所以先校验完整节点身份。重复任务ID会被拒绝，重复前置也会被拒绝，避免上游问题被静默合并。

小问题：B依赖A，A状态缺失，可不可以默认A已经完成？不能，应补齐证据或修正任务表。

## 3. 什么是拓扑顺序？

**拓扑顺序**是一种排列，保证每个前置出现在后续之前。A→B→C时，A、B、C是合法顺序。若D也只依赖A，A、D、B、C也合法。拓扑顺序可能有多个，不必要求每次只得到一种字符串排列。

可以用入度手推。**入度**是在当前尚未移除的图里，一个节点还有多少前置边。先选入度为零的节点，把它从结构图移除，再减少其后续节点的入度。反复执行，能处理全部节点就有完整拓扑顺序。

| 步骤 | 尚需前置 | 可移除 |
| --- | --- | --- |
| 初始 | A无，B等A，C等B，D等A | A |
| 移除A | B无，C等B，D无 | B、D |
| 再移除B、D | C无 | C |

“移除”只是算法中的结构操作，不会把真实任务改成done。计算一个合法未来顺序和读取实际完成证据，是两项不同动作。

## 4. 循环如何阻塞？

如果A依赖B，B又依赖A，两者都有尚未满足的前置，结构上无法排列。称为**有向环**。自依赖A→A也是环。

TopologicalSorter在准备或迭代时会抛CycleError。本例捕获异常，保存库返回的一条循环示例，结构顺序设为空。它没有枚举所有环，也没有自动删除某条关系来凑出结果。修复关系需要业务人员确认。

若另有独立任务X，理论上可单独处理X。当前MVP选择保守策略，发现任意循环就让全部候选列表为空，报告交人工审查。需要局部调度时应显式扩展策略和验收，不能悄悄改变“就绪”口径。

## 5. 当前就绪与结构顺序

样例A已完成，B待处理依赖A，C待处理依赖B，D进行中依赖A。当前依赖条件满足的待处理任务只有B。C等待B。D已经在执行，不列为新的待处理候选。

可写为一条判断。

```text
候选 = 状态为pending，且每个前置状态为done，且本例全局无环
```

“且”要求三项都成立。即使满足，还缺真实资源、权限与正式派工规则。函数输出dispatch_authorized=false，后续业务不能把候选列表直接当执行令牌。

如果C被标记done而B仍pending，程序把C列入inconsistent_active_or_done。它提示状态快照需要调查，不自动认定员工做错，也不修改记录。可能是数据延迟、状态语义不同或依赖配置错误。

## 6. 逐段读实现

以下片段需结合完整文件阅读。

```python
predecessors = {key: tuple(sorted(tasks[key]["requires"])) for key in sorted(tasks)}
order = list(TopologicalSorter(predecessors).static_order())
```

输入是已校验的任务映射。第一行固定节点与前置顺序，便于重现；第二行把生成的结构顺序收集成列表。排序只提供稳定的输入次序，不表示高优先级或最短工期。

```python
unfinished = [dep for dep in sorted(row["requires"]) if tasks[dep]["status"] != "done"]
```

输入是当前任务的前置ID，动作是查状态，输出尚未完成的前置列表。它只检查直接前置。若B等待A、C等待B，C的直接阻塞是B，沿原始关系可以继续调查A。本例不额外生成全传递阻塞闭包。

空前置列表表示当前图中没有前置条件。所有条件是否已录入，仍取决于来源覆盖。图算法无法推导一个被漏写的业务规则。

Python3.11+与完整仓库，无额外依赖、模型或GPU。PowerShell进入仓库根目录后运行[完整例子](examples/dependency_order_lab.py)。

```powershell
python knowledge-base/examples/dependency_order_lab.py
```

按源码推导的预期如下，本次未执行课堂脚本。

```text
ready: ['TASK-B']
waiting: TASK-C
cycle: False
cycle example: True
```

只把TASK-A改成pending，B应转入等待，正在执行的D会出现未完成前置矛盾。只把C改成done，会报告C的状态矛盾。给A加前置C会构成环，候选列表为空。三个单变量变化对应三种不同问题。

找不到agent先核完整仓库。Unknown prerequisite表示依赖指向未录入节点，应修数据。Explicit offset required表示审核时间缺少时区偏移。不要把这些输入错误归因于模型。

## 8. 工程取舍

本例最多100任务、500依赖，使用内存字典和标准库足够。大图、频繁更新或跨版本审查可能需要数据库索引、版本快照和异步作业。输出计算时刻的候选，执行前仍应核最新状态和权限。

TopologicalSorter还提供prepare、get_ready、done等接口用于动态推进。done表示调用方告知任务已处理，必须由可信执行结果驱动，不能为了释放下游就直接把所有节点标完。本例仅使用static_order审结构，未接执行器。

算法维护状态的成本随节点、边和输出增长。排序和来源整理也消耗资源，不把理论复杂度写成实测性能。12项工具验收源码覆盖样例、方向、环、重复、缺失、版本与时效，运行结果待手动验收。

## 9. 练习与解释性答案

1. 两种顺序都满足前置关系，哪个一定错？都可能合法，还需业务优先级规则。
2. 依赖审查能自动算最短工期吗？本例没有工时和资源输入，因此无法求解排程目标。
3. 图无环，但全部pending，有哪些可候选？没有前置的pending节点，且其他规则仍需另核。
4. C已done但B未done，应自动回退C吗？先调查快照、状态定义和配置，工具只报告矛盾。
5. 一个CycleError能代表所有环吗？它提供一个循环示例，不能声称全量环清单。
