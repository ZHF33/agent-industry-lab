# 第十一讲：请求超时了，订单到底有没有创建？

配合API调用失败分诊Agent，解释HTTP响应、传输失败和业务结果。

## 1. 从电话订餐开始

你打电话下单，对方听到了地址，电话突然断掉。你没听见“订单已收”，不代表厨房没开始做。如果立即再打一次重新下单，可能得到两份餐。

API类似程序之间的服务窗口；HTTP是它们常用的请求/响应规则。**超时**表示调用方在规定时间内没等到某个阶段的响应，不等于业务没执行。类比边界：真实系统可能经过多个代理、队列和服务，失败点更多，不能只看一条连接错误就确认整个业务链结果。

小问题：付款或下单超时，应该立刻重复提交吗？不能，先用已有业务编号查询状态，结合接口幂等契约处理。

## 2. 三件事分开看

第一，是否收到HTTP响应？第二，HTTP状态是什么？第三，业务是否完成？收到200只表示HTTP响应成功范围，业务正文仍可能说明任务待处理。收到202也不等于任务已结束。没有响应更不能直接推导失败。

**状态码**是HTTP响应里的一组数字。401通常涉及认证，403涉及授权或策略，429表示请求过多，5xx表示服务端或网关阶段问题。实际含义仍要结合接口契约与返回信息，不能凭一个503就断言数据库坏了。

项目把超时标outcome_unknown，把连接类问题与HTTP状态分类分开。业务写操作统一要求核对后再考虑重提，模型不执行任何重试。

## 3. 为什么所有失败都重试不行？

重试是再发一次请求。它可能解决短暂抖动，也可能加重限流、重复扣款或掩盖权限错误。401和403一般需要检查凭据与授权，不该反复发送同样请求。429要遵守服务端等待规则，不能越忙请求越密。5xx也需要考虑操作是否有副作用。

GET/HEAD通常用于读取；POST常用于提交业务，但方法名不能替代真实接口语义。本例采取保守简化：只读方法的瞬态问题才列为人工考虑重试，所有写请求先核对。没有提供自动执行器，因此“候选”不是动作授权。

## 4. 代码如何分开判断？

说明片段，不可独立运行：

```python
read_only = incident["method"] in ["GET", "HEAD"]
candidate = status in [429, 502, 503, 504]
review_retry = candidate and read_only
```

输入是操作方法与状态码，第一步判断本例的只读范围，第二步找演示策略里的瞬态状态，第三步合并两个条件。实际工具还支持timeout和connection_error，并输出automatic_retry=false。这个布尔值意味着程序根本没有执行重试，而不是已经证明任何重试都安全。

对于POST超时，程序输出reconcile_before_resubmitting=true。reconcile可以理解为核对业务记录：先确认原始请求对应的订单、支付或任务。没有可查询业务编号、没有幂等契约时，应升级人工处理，不让模型猜“应该没成功”。

小问题：接口文档写支持幂等，是否随便换个键重提？不能，换键可能被当作新业务。相同逻辑操作如何保留原键，要按接口契约明确，本讲不重复第一讲完整机制。

## 5. 观察与执行为什么分开？

这个Agent读取合成操作、合成响应和策略，模型自主调用工具，计算分类后带来源交人工审核。它没有业务HTTP调用工具，因此不会真的重发订单。人工approve只接受调查建议，也不代表获得支付、权限修改或客户通知能力。

真实接入可把监控系统的脱敏观测送来，但需身份和对象权限、数据保留及审计。错误正文可能包含客户信息、URL参数和令牌，不能把原日志直接上传公开仓库。仅记录必要错误类别与受控关联编号。

## 6. 最小实验

Python3.12+，无第三方依赖、无实际网络请求。在仓库根目录执行：

```powershell
python knowledge-base/examples/failure_lab.py
```

预期输出GET 503 review_retry、POST timeout reconcile、POST 403 investigate。函数接收操作和观测，按最小规则给出建议标签。它不是重试器，也不建立HTTP连接。本次只做语法检查，不编造实际运行结果。

## 7. 故障排查与工程选择

不断401：检查凭据配置，不把令牌写进日志。403：确认实际账号是否拥有目标仓库或业务对象权限，连接成功不等于写权限。超时后两份订单：检查有没有保留业务编号和幂等键。服务越来越慢：检查是否层层重试造成放大，不只把超时调更长。

本仓库模型每次HTTP请求有120秒限制，图最多四轮；n8n等待510秒。链路上若另有更短代理超时，外层可能先断，而后端仍在处理。当前提交接口没有幂等去重，所以文档明确不能盲目重提。要用于长任务，应考虑任务队列与查询结果入口，不能仅把同步等待无限延长。

队列、Redis或容器不是所有错误的答案。先定义操作语义与失败分类，再按并发、等待和恢复需求引入组件。后续深入退避、抖动、熔断时，仍必须先确认哪些操作允许重试。

## 8. 练习与解释性答案

一：503证明数据库故障吗？不证明，只说明某阶段服务不可用，需要更多证据。

二：POST超时代表没有订单吗？不代表，结果未知，先核对业务状态。

三：重试候选等于自动执行吗？不是，当前工具明确不执行。

四：GitHub已连接却推送403，重复请求能解决吗？不能，先确认使用账号和写权限；这正是认证与授权的区别。

五：把HTTP超时改成一小时就可靠了吗？不，外层等待、资源占用、结果查询和重复提交风险仍要设计。
