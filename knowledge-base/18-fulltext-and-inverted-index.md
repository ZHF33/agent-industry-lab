# 第十八讲｜搜到关键词，就找对政策了吗？全文检索与倒排索引

本课对应[客服知识证据审查Agent](../examples/support-knowledge-review/README.md)。不用数据库，不下载模型，不接真实客服系统。核心是看清“词出现在哪里”与“政策适不适用”的差别。

## 1. 先从书后的索引看起

翻一本维修手册，想找“杯子破损退货”，可以逐页扫描，也可以先看书后索引：“破损→12、35页；杯子→8、12页”。索引先告诉你去哪几页，不替你判断那段话究竟是允许、禁止还是已经作废。

**检索（retrieval）**是从资料集合找出候选内容。**全文检索（full-text search）**通常把文字拆成可查找单位，建立可搜索结构，再按查询返回候选。这里“全文”不表示必定搜索所有权限之外的内容，也不表示全文一定全部返回。

类比边界：真实索引还保存位置、频次、字段及更新结构，排序可比书后页码复杂。今天先用最小索引把方向讲清。

自查：搜出“旧政策不再允许退款”，能只因它包含“允许退款”就自动承诺客户吗？不能，命中不等于肯定，更不等于当前适用。

## 2. 正排和倒排，是同一件事的两个方向

**文档**在本课指一小段可引用文字，不一定是一整本PDF。每段有来源ID。先用三个合成段落：

| ID | 正文 |
| --- | --- |
| A | damaged mug return |
| B | damaged plate return |
| C | mug care |

从文档找词叫正向看：A里有damaged、mug、return。**倒排索引（inverted index）**把方向反过来，从词找包含它的文档。

| 词 | 文档集合 |
| --- | --- |
| damaged | A、B |
| mug | A、C |
| return | A、B |
| plate | B |
| care | C |

**集合**是一组不重复元素；本例同一词在A出现十遍也只记一次A。真实全文引擎可以额外记录出现次数与位置，本例有意先省去它们。

小问题：为什么叫倒排？原来是“文档→词”，现在是“词→文档”。不是把文字倒着写。

## 3. 查询先变成哪些词？

本例用一个明确的教学规则：转小写，再用`[a-z0-9]+`提取连续英文字母或数字，最后去重。`Mug, mug!`得到一个mug。这个过程属于**词项分析**，在真实引擎中由分词/分析器承担。

注意不要混淆第五期大模型Token：检索分析器输出的词项和模型分词器输出的词元不保证相同。这里也没有中文分词；`杯子破损`不会产生可用词项。不得说支持多语言全文。

另一个边界：`mug`与`cup`意思可能相近，但这个规则看的是词形，不会自动理解同义词。“broken cup”找不到“damaged mug”，不是模型忘了知识，而是本例没有语义扩展路径。

## 4. 并集找到候选，交集数帮助排序

查询是damaged mug return。三个倒排表的并集是A、B、C；**并集**表示出现在任意一个表里即可成为候选。

本例分数定义为：

```text
score(q,d) = 查询词集合q 与 文档词集合d 的交集大小
```

**交集**是两边都有的词；竖线常用来表示集合大小，这里直接用中文说清。A有三个共同词，得3；B有damaged、return，得2；C有mug，得1。排序为A、B、C。

这是手工可核对的“不同词项重合数”，不是BM25。若改成必须三个词全有，即AND逻辑，只剩A；当前脚本采用OR找候选，再按分数排序。两者不能混写。

练习：把查询改成mug return。A=2，B=1，C=1；同分时按来源ID排序得到A、B、C。业务上B可能仍不适用，分数没解决产品范围问题。

## 5. 先限制范围，再考虑返回谁

假设B属于另一个产品，即使词很多也不能给当前杯子请求当依据。我们定义可访问候选集合`allowed={A,C}`，结果变为A=3、C=1。

真实系统里的**元数据过滤**可以包括租户、产品、地区、生效日期、发布状态。产品或地区匹配不等于访问授权；用户身份与权限必须由可信业务层决定，不能让请求者写一个tenant_id就读别人资料。

尤其不能先全局取top1再过滤：如果B排第一而不允许，过滤后可能为空，尽管A原本也相关。应在检索设计中落实权限/元数据过滤与足够的候选召回；具体引擎支持的预过滤、后过滤和代价需要评估。

Agent本例是先在小数组中严格筛合成范围，再按词项评分。没有真实用户权限系统，不能把它包装成已完成企业知识隔离。

## 6. 最小离线实验

前提：Python 3.11+，不装额外包。PowerShell是输入命令的窗口，`cd`用于切换目录。先进入仓库根目录：

```powershell
python --version
python knowledge-base/examples/lexical_search_lab.py
```

完整例子：[lexical_search_lab.py](examples/lexical_search_lab.py)。下面是按源码推导的预期，未实际执行：

```text
mug: A,C
all: [('A', 3), ('B', 2), ('C', 1)]
scoped: [('A', 3), ('C', 1)]
synonym: []
```

第一行查mug的倒排表；第二行不加业务范围过滤；第三行排除B；第四行暴露同义词短板。输出空列表不是“世界上没有答案”，只说明当前分析规则与资料下没找到匹配。

## 7. 代码分段讲

以下都是完整文件中的片段，不能单独运行：

```python
for source, text in documents.items():
    for term in terms(text):
        index.setdefault(term, set()).add(source)
```

输入是ID到正文的字典。外层for逐文档，内层for逐词项。`setdefault`在没有这个词时新建空集合；`add`把来源ID记进去。因此mug最后关联A和C。

```python
candidates.update(index.get(term, set()))
```

`get`查一个词，查不到就返回空集合；`update`合并候选。这里没有相似词匹配，也没有调用模型。

```python
for source in candidates & allowed
```

`&`在集合上表示交集，只保留既命中又在allowed里的文档。然后对每个候选统计查询词在哪些倒排表里存在，得到分数；`(-score, source)`表示分数越大越靠前，同分按ID。

别只记语法：关键输入是资料/查询/允许范围，动作是建索引/取候选/过滤/计分，结果是候选列表，不是最终业务决定。

## 8. 从玩具到真实全文引擎，缺了什么？

索引减少重复逐篇扫描的需要，但代价是额外空间与维护。新增资料、更新正文、撤下旧政策，必须保证查询不继续使用错误版本。数据库存储更新成功也不能自动证明外部索引已同步。

真实排序往往使用词频、逆文档频率和文档长度等信号。例如BM25会考虑一个词在文档中出现频次、在整个语料中是否稀有及文档长短。本例只数不同词重合，不具备这些机制。

SQLite FTS5提供全文查询和BM25辅助函数；其实现为了默认升序方便，分数越小通常匹配越好。这是该实现的约定，不能拿“本例越大越好”直接套上去。[FTS5官方资料](https://www.sqlite.org/fts5.html)

本课没有创建SQLite文件，也没有接入FTS5。后续接入要另外核实编译特性、中文分析、查询语法、参数化SQL、索引更新与授权过滤，不能把这份字典称作数据库索引性能实验。

## 9. RAG为什么还需要下一步？

**RAG（检索增强生成）**把找到的资料作为生成的依据之一。检索只能给候选，生成还要处理问题、证据关系与不足。

今日Agent走的是最小路径：固定合成请求→限定范围检索→带source返回片段→模型读结果起草→人工审核。没有向量库也可以有检索增强路径；但不代表向量检索没有价值。同义词、长文档、跨语言可能需要更好的分析、语义检索或混合方案。

引用也分层：ID确实存在、内容确实来自该ID、这句话确实支持结论、政策确实适用订单，是四种不同检查。当前图只强制存在候选引用，未自动验证全部蕴含关系；人工必须看原文，不能因带链接就认为可信。

## 10. 故障识别与选型

| 情况 | 可能原因 | 优先动作 |
| --- | --- | --- |
| broken cup搜不到damaged mug | 词形不同 | 测同义词需求，设计查询扩展或语义路线 |
| 中文没结果 | ASCII分析器不支持 | 明确边界，选中文分析器并验收 |
| 旧政策排前面 | 未过滤生效日期/状态 | 先核元数据与版本 |
| 高频通用词淹没结果 | 排序过简 | 评估停用词、词权重和长度归一 |
| 排名高却答非所问 | 否定、条件、对象不同 | 阅读上下文，做证据支持与适用判断 |
| 同一查询结果波动 | 索引更新、同分排序不稳 | 记录版本并固定同分规则 |

命令找不到python是环境问题；找不到脚本先核工作目录；与检索零命中要分开处理。小语料先用明确词法基线，能帮助发现数据问题；规模和需求增长后用成熟全文引擎，别自己无意重造搜索服务。

## 11. 作业与解释性答案

1. A把mug重复三遍，本例score会增加吗？**不会。**词项用集合去重；不是词频排序。
2. 只搜return时A和B谁排前？**A。**都得1，按ID稳定排序；这不证明A政策更权威。
3. allowed只含C，结果是什么？**C得1。**它可能只是保养文档，不能因为只剩它就当退货答案。
4. 没有命中时能让模型编一个“合理政策”吗？**不能。**应说证据不足，补充查询、资料或人工判断。
5. 过滤了产品和地区是否完成租户权限？**没有。**可信身份、租户授权和资源范围还须独立实现。
