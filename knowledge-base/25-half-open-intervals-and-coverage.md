# 第25讲　交班记录重叠时，覆盖时长怎么算？

工厂班组长拿到三条交接记录。每条都有开始、结束和来源。有人把时长相加，有人看到记录总时长超过四小时就以为全程有证据。两种做法都可能错，因为记录可以重叠，也可能跨过班次边界。学完这讲，你可以手算真实的证据覆盖，并解释缺口的含义。配套案例为[交班覆盖 Agent](../examples/shift-coverage-review/README.md)。

## 从预约表理解区间

想象借一间会议室，上午八点到九点和九点到十点可以连续预约。我们用半开区间 `[开始, 结束)` 表示，方括号包含起点，圆括号排除终点。九点属于后一段。业务约定可以不同，今天的实现采用这个约定。

类比的边界在于预约表只表达计划。交班工具同样只看当前记录，缺口提示证据不足，实际发生的活动要另查。

小问题：两段在九点接上，中间是否空了一分钟？答案是零分钟。左段到九点结束，右段从九点开始。

## 先把时钟对齐

带偏移的时间字符串写明它比 UTC 早或晚多少。UTC 是统一的时间基准。05:00−05:00 与 10:00Z 指向同一时刻。代码解析后统一转 UTC 再比较。缺少偏移的 05:00 无法确定对应时刻，程序报错。

偏移描述输入所指的具体时刻。由“某地每天早上八点”生成时间则需要当地时区规则，还可能遇到重复或不存在的钟表时刻。这一版要求上游提交带偏移的时刻。

小问题：同一张表的两个字符串能否直接按字母排序？答案取决于格式与偏移是否一致。这里先转为时间对象，避免把表面顺序当成时间顺序。

## 裁剪，再合并

班次窗口记作 `[L,R)`，记录记作 `[a,b)`。交集左端是 `max(L,a)`，右端是 `min(R,b)`。左端小于右端才有正长度。max 取较晚时间，min 取较早时间。

样例窗口是 08:00–12:00 UTC。三条记录经过裁剪后如下。

| 记录 | 原始时间 | 窗口内时间 |
| --- | --- | --- |
| A | 07:50–09:00 | 08:00–09:00 |
| B | 08:45–10:00 | 08:45–10:00 |
| C | 10:20–12:10 | 10:20–12:00 |

A、B 重叠 15 分钟。裁剪后直接相加得到 60+75+100=235 分钟。正确做法是按开始时间排序，把 A、B 合成 08:00–10:00，再加 C 的 100 分钟，得到 220 分钟。窗口 240 分钟，剩下 20 分钟是 10:00–10:20。

小问题：把 B 改成 08:45–09:00，A、B 合并后结束时间是什么？仍是 09:00，因为合并端点取两段较晚的结束时间。

## 从代码读出算法

以下为项目片段，需结合完整文件阅读。

```python
a, b = max(a, left), min(b, right)
if a < b:
    clipped.append((a, b, source))
```

输入为记录和目标窗口。动作是保留交集及来源，结果是窗口内一批可排序的区间。

```python
if merged and a <= merged[-1][1]:
    first, last, sources = merged[-1]
    merged[-1] = (first, max(last, b), sources + [source])
```

最后一段若与新记录重叠或相接，就扩展结束时间并保留来源。完全被包含的记录也会贡献来源。由于已经排序，只需检查最后一段。最后用游标从窗口左端扫过，遇到下一个起点晚于游标就记下缺口，最后还检查窗口尾部。

`来源列表` 是合并段的参与记录。若要证明某一分钟由哪一条记录覆盖，需要回看原始端点。当前报告保留来源 ID，原始端点在取证工具结果中。

## 上线前怎么选

小快照用内存排序和扫描即可。大规模区间查询可考虑数据库索引与分页，但必须保证分页边界不会拆漏重叠。排序通常占主要成本，本实现还复制来源列表，因此对输入限制 100 条。它只处理已结束班次和固定快照，跨班次汇总需先明确窗口划分。证据新鲜度与区间覆盖是两个独立信号。

1. 两段 08:00–08:30、08:15–09:00 覆盖多久？60 分钟。重叠部分只计一次。
2. 一条记录恰好在窗口开始时结束，贡献多久？零。交集左右端相等。
3. 快照声明完整但有缺口，能否认定无人值班？仍需复核原始记录及实际交接。报告只说明证据状态。
4. 合并后覆盖加缺口应等于多少？窗口全长。可用这一关系检查漏算尾部。

交付练习为手画三段时间轴，圈出重叠，算出并集与缺口，再写一句业务解释。
